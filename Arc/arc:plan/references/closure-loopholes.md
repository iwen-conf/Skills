# 漏洞推演清单（脚本之外的人工检查）

脚本只检查所建模型。下面这些问题需逐条对照业务来源推演：设计模式登记到 `05-loophole-register.md`；
审查模式仅登记到 `.arc/artifacts/<task-slug>/closure/loopholes.md`。
按 [Arc 协作合同](../../_shared/workflow.md) 把运行时断言交 `arc:verify`，模型覆盖不得写成运行时已验证。

**每一条必须落到三种结论之一：**
- ✅ **模型已覆盖**：写明在 spec 哪里（流转 id / 不变量 id / 场景名），运行时证据另列
- ⛔ **不适用**：写明为什么不适用（一句具体理由，不能写"不涉及"）
- ❗ **缺口**：登记为漏洞，写严重度和处置（补进 spec / 需用户决策 / 接受风险并由用户确认）

不要整类跳过。未知项登记为 `needs-triage` 或 `manual-gap`，附缺失证据；仅未决业务假设、豁免和范围
决策需要用户判断。已授权的检索、核查和验证交对应 Arc 阶段继续，不重复索取授权。

## 目录

1. 需求与范围　2. 角色与权限　3. 数据生命周期　4. 异常与补偿　5. 并发与一致性
6. 资金/库存/额度　7. 时间　8. 运维与兜底　9. 通知与反馈　10. 边界值　11. 变更与兼容

## 1. 需求与范围
- 需求里每个"谁能做什么"，在 spec 里都有对应的角色和流转吗？
- 需求没说、但业务必然存在的角色有没有？（管理员、客服、运营、审计、系统自身、外部系统）
- 每个需求的"失败/拒绝/撤销"情形有没有被讨论过，而不只是成功路径？
- 范围外的东西（本期不做）有没有明确记录，并确认它们不会让本期业务出现死胡同？

## 2. 角色与权限
- 每条流转的执行角色是否合理？有没有"谁都能触发"的敏感操作？
- 越权：A 能否操作属于 B 的对象？数据范围（自己的/部门的/全部）是否在业务里定义了？
- 高风险操作（退款、删除、改价、批量操作）是否需要二次确认/审批/留痕？
- 角色被禁用/离职/权限被收回时，他手上未完成的事（待办、持有的对象）谁接手？

## 3. 数据生命周期
- 每类数据：谁创建 → 谁使用 → 何时失效/归档/删除？有没有"只增不减"的数据？
- 删除是物理删还是软删？被引用的数据能不能删？删了引用方怎么办？
- 状态变化时，历史快照需要保留吗（价格、地址、规则版本）？
- 对外承诺的数据（订单金额、合同内容）事后能被改吗？谁改、留痕吗？

## 4. 异常与补偿
- 每个调用外部系统的流转：外部超时、返回失败、返回成功但我没收到（"成功但未知"），分别怎么处理？
- 多步操作中间失败：已完成的前几步如何补偿/回滚？有没有"半成功"的最终状态？
- 重试：谁重试、重试几次、间隔多久、重试耗尽后去哪？重试是否幂等？
- 每个"人工处理"状态：谁来处理、多久内、超期怎么办、处理完怎么回到主流程？

## 5. 并发与一致性
- 重复提交/重复点击/重复回调：同一个请求来两次，结果是否和来一次一样（幂等键是什么）？
- 两个角色同时操作同一对象（R20 的竞态点）：裁决策略落地方式是什么（乐观锁/状态校验/唯一约束）？
- 跨实体的一致性：是强一致（同事务）还是最终一致？最终一致的窗口期里，用户看到的是什么？有对账吗？
- 多实例争抢：多个订单抢同一库存/名额/优惠券，会不会超卖/超发？（脚本不覆盖多实例）

## 6. 资金/库存/额度
- 每种"占用/冻结/扣减"都在 resources 里建模了吗？所有结束路径都释放/结算了吗？
- 对账：系统记录与外部（支付渠道、仓库）记录不一致时，发现机制和修复入口是什么？
- 金额/数量的精度、币种、舍入、负数、上限，有没有约定？
- 退款/冲正能否超过原额？部分退款后的剩余怎么处理？

## 7. 时间
- 每个 timer：触发时间怎么算（以谁的时钟、哪个时区）？定时任务漏跑/重复跑怎么办？
- 超时后到达的"迟到"事件（R17 已查状态层面）——业务层面是否需要补偿或通知？
- 有效期/过期：到期前提醒、到期后的处置是否完整？

## 8. 运维与兜底
- 任何卡住的单据，运营有没有入口人工推进/强制终结（并留痕）？
- 失败队列/死信：谁看、多久看、怎么重放？
- 数据修复手段：出了脏数据怎么订正？订正动作本身是否留痕、可审计？
- 关键状态长时间不变的监控与告警（对应 R19 的兜底）是否有承接？

## 9. 通知与反馈
- 每个终态变化（尤其异常终态：取消、失败、退款）相关方都能知道吗？通过什么渠道？
- 异步结果（支付、审核、退款）用户在哪里看到进度？失败时看到的是什么、能做什么？

## 10. 边界值
- 空、0、负数、超长、超大批量、重复元素、特殊字符/Emoji、时间边界（跨日/跨月/闰年）。
- 数量上限：单对象下子项上限、单用户并发上限、批量操作上限，达到上限后的行为。

## 11. 变更与兼容
- 将来新增一个状态/事件，已存在的在途数据怎么迁移？
- 规则变更（价格、策略）对在途单据生效还是对新单据生效？
- 接口/数据格式的版本兼容；灰度与回滚时两套逻辑并存期的状态是否会冲突？

## 严重度参考（登记漏洞时用）

| 级别 | 含义 | 例 |
|---|---|---|
| Critical | 主路径数据损坏、丢失或整体不可用 | 确认重复扣款或不可恢复资金损失 |
| High | 主路径错误结果、现有业务合同破坏 | 退款失败无合同要求的补偿或兜底 |
| Medium | 边界缺陷或局部影响 | 特定时序通知丢失，有明确绕行方式 |
| Low | 有明确规则依据的可维护性问题 | 同一状态策略重复且已经发生维护分歧 |
| Info | 文档差异或加固建议 | 无已确认行为缺陷的说明补全 |

严重度由实际影响及证据决定，历史 S1–S4 记录保留来源并重新按 Arc 合同评估，不机械换名。
Critical/High 不得以“接受风险”关闭，除非用户明确书面确认；已有确认可引用，无需重复询问。
Finding 状态沿用 `confirmed` / `likely` / `needs-triage` / `false-positive` / `manual-gap`。
