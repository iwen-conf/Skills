# spec 格式（03-closure-spec.yaml）

通用格式，与具体业务无关。换业务只换内容。所有名称（角色、实体、状态、事件）用同一套中文或英文，**全 spec 内保持一致**（脚本按字面量匹配，写错就是 R6 报错）。

## 目录

1. 顶层结构
2. actors 角色
3. requirements 需求
4. events 事件
5. resources 资源
6. entities 实体（核心）
7. scenarios 场景
8. invariants 不变量
9. waivers 豁免
10. 建模指南：怎么从需求里找出这些东西

## 1. 顶层结构

```yaml
meta:          {system: 系统名, version: "0.1"}
actors:        {角色名: {kind: human|system|external}}
requirements:  {REQ-001: 需求描述}
resources:     {资源名: 说明}                # 可选
events:        {事件名: {source: ..., ...}}
entities:      {实体名: {...}}
scenarios:     {场景名: {...}}
invariants:    [ {...} ]
waivers:       [ {...} ]                      # 可选，慎用
```

## 2. actors

| kind | 含义 | 例 |
|---|---|---|
| human | 真人操作者（需要反馈，见 R18） | 用户、管理员、客服、运营 |
| system | 本系统自己（定时任务、联动处理） | 系统 |
| external | 外部系统/第三方 | 支付渠道、物流、短信网关 |

## 3. requirements

`REQ-编号: 一句话描述`。每条需求必须被至少一个场景覆盖（R12），每个场景必须关联需求。需求要写成"业务结果"，不要写成"功能点"。

已有 PRD 时沿用其稳定 ID（不强制重新编号为 REQ-001），值只写摘要；完整来源链接登记在
`01-requirements.md`。机器模型不取代原需求，执行任务和验证证据通过这些 ID 关联。

## 4. events

```yaml
事件名:
  source: actor | external | timer | internal
  after: 30分钟        # source 为 timer 时必填
  desc: 说明           # 可选
  sinks: [{kind: notify, target: 用户, desc: 通知}]   # 可选：不引起状态流转的消费者（通知/审计/报表）
```

| source | 含义 | 到达特性 |
|---|---|---|
| actor | 人在界面/接口上主动操作 | 同步；状态不允许时直接被拒绝，不算漏处理 |
| external | 外部系统回调/消息 | **异步，可能迟到、重复、乱序**（R17 严查） |
| timer | 超时/定时任务 | 异步，**可能在任何状态触发**（R17 严查） |
| internal | 本系统某个流转 `emits` 出来的联动事件 | 由联动产生（R5 要求必须有人发出） |

## 5. resources

需要"占用后必须释放/消耗"的东西：库存占用、资金冻结、优惠券占用、名额、锁、临时文件……流转用 `acquires: [资源]` / `releases: [资源]` 标记。脚本在所有路径上核对：终态不得残留占用（泄漏）、不得在未占用时释放（重复释放）、不得重复占用。

## 6. entities（核心）

```yaml
实体名:
  created_by: {event: 事件, actor: 角色, emits: [事件], acquires: [资源]}   # 谁、因什么事件创建它
  states: [状态...]            # 完整列表（用来抓拼写错误和孤立状态）
  initial: 状态                # 创建后的初始状态，有且仅有一个
  terminal: [状态...]          # 终态：生命周期结束，不能再有出边
  transitions:
    - id: X-01                 # 全局唯一
      from: 状态
      event: 事件
      actor: 角色
      to: 状态
      kind: normal | exception # 默认 normal；取消/拒绝/超时/失败/回滚/退回 一律 exception
      guard: "条件"            # 同一(from+event)有多条流转时必填且互斥（分支）
      emits: [事件...]         # 流转后发出的联动事件
      feedback: "操作后谁在哪看到什么"   # human 角色必填（R18）
      acquires: [资源]
      releases: [资源]
      terminates_by: "..."     # 仅当处在事件联动环里时填，说明为何会终止（R13）
  ignores:                     # 声明"此状态下收到该异步事件可安全忽略"（R17）
    - {event: 事件, states: [状态... | "@terminal" | "@others"], reason: 必填}
  race_policy: {状态: "并发事件同时到来时谁优先、败者怎么处理"}   # R20
  fields:                      # 数据字段（R9）
    字段名: {writers: [流转id | "@创建" | "@外部来源"], readers: [流转id | "@页面" | "@报表"]}
```

要点：
- **创建也是事件**：`created_by.event` 可以是 actor（用户提交）或 internal（别的实体联动创建它）。
- `ignores.states` 的两个快捷词：`@terminal`＝所有终态；`@others`＝该实体中所有"对这个事件没有处理流转"的状态。用 `@others` 等于宣称"其余情况根本不会发生/无害"，理由要写得站得住，评审时重点看（报告里有"忽略清单"）。
- `fields` 的 writers/readers：写流转 id（脚本核对存在）；来自/用于流转之外的（页面展示、报表、导入）用 `@` 开头的自由文本。
- 状态名别用 `是/否/on/off/yes/no/null`（YAML 会变布尔/空），要用就加引号。

## 7. scenarios

```yaml
场景名:
  type: normal | exception
  entity: 主实体               # 这个场景的"主角"，它必须从初始态走到终态
  req: [REQ-001]
  steps: [流转id, ...]         # 按发生顺序；可跨实体（联动产生的流转也要列出）
```

脚本核对：每个实体首次出现的步骤从初始态出发；同一实体相邻步骤首尾衔接；internal 事件触发的步骤，其事件必须已被前序步骤发出；主实体最终停在终态；**每条流转至少被一个场景覆盖**；每个实体至少有一个异常场景。

## 8. invariants

```yaml
- id: INV-01
  desc: 订单已取消时，库存不能还被占着
  when: {订单: [已取消]}                 # 全部条件成立时……
  then: {库存锁定: [已释放, 已回库]}      # ……这些必须成立。"@none" 表示实体尚未创建
```

不变量表达"跨实体必须同时成立的事实"，是抓联动漏洞最有力的工具。只在**稳定状态**（联动全部处理完）上检查。写不变量的提示：每个资金/库存/额度/权限类事实、每对"A 的状态蕴含 B 的状态"的关系都写一条。

## 9. waivers

```yaml
- {rule: R19, target: 支付单.待人工退款, reason: 具体理由}
```

`target` 必须与报告里该问题的"对象"逐字一致；未命中任何问题的豁免会被报为 W 警告。R6（格式/引用错误）不可豁免。

豁免理由及其已有确认依据登记到漏洞表；未确认的业务例外不能解锁实现。豁免不能把跳过的动态检查、
截断状态空间或未运行的产品测试变成 PASS。严格模型 gate 同时检查执行完整性和 spec/检查器指纹。

## 10. 建模指南

1. **实体** = 有生命周期、会被反复提及的名词（订单、工单、申请、支付单、库存占用、账号……）。判断标准：它有"从无到有再到结束"的过程。只是属性的东西（地址、备注）不是实体，放进 `fields`。
2. **一个实体一个状态机。** 把"订单的支付情况"这种另一条生命线拆成独立实体（支付单），靠事件联动，别塞进同一个状态里导致状态爆炸。
3. **事件** = 引起状态变化的"发生了什么"：用户操作、外部回调、超时、别的实体的状态变化。先问"谁/什么让它变的"，再命名。
4. **每个等待态都要问三遍**：对方不来怎么办（超时）？对方说不行怎么办（拒绝/失败）？我自己想撤回怎么办（取消）？
5. **每个"占用"都要问**：谁释放？所有结束路径（成功、取消、超时、失败）都释放了吗？→ resources。
6. **每个异步事件都要问**：它迟到、重复、在对象已结束后才到，怎么办？→ 处理流转或 ignores。
7. **跨实体的"必须一致"** 都写成不变量。
