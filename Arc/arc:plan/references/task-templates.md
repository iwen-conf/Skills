# Task Document Templates

Read only when creating or rewriting a task entry, `00-前置约束.md`, group README, work-package
README, leaf card or progress tracker. Rules: [task-docs.md](task-docs.md). Replace every example
name, path, rating and command with discovered project facts; keep the Chinese headings as written.
Create only the work packages in scope.

## Task entry — `NN-具体任务名/README.md`

```markdown
# 具体任务名

本文是任务入口。具体任务和进度在当前目录。

## 使用方式

1. 先看 `00-前置约束.md` 和 `进度跟踪表.md`；两者就绪前不改代码。
2. 按“业务任务组 → 工作包 → 子任务”打开当前任务；每个子任务单独验收。
3. 开工前重新核对影响文件、依赖和测试，先执行任务卡中的 `<Context-Queries>`；项目已变化时先回写前置约束、任务卡和进度表。
4. 状态在进度表和任务卡中同一次修改同步：开始 `[/]`；改完待验证 `[?]`；验证通过 `[x]` 并写命令和结果；阻塞 `[!]` 写明原因和需谁处理；放弃 `[-]` 写明原因和重启条件。
5. 进度表过期时不继续实施；进度表未反映最终状态前不做交付回复。

## 需求来源

1. [需求名称](../../00-产品需求/NN-需求名称.md)

## 设计边界

1. ...
2. 系统设计：链接到当前设计文档。
3. 接口基准：链接到 `docs/02-API记录/` 中的 Markdown 契约及章节。

## 拆分依据

1. 主要难点：当前业务状态、契约/数据风险、依赖与验证成本。
2. 分层：业务任务组 → 后端/前端工作包 → 独立验收的子任务。
3. 分端：后端和前端各自交付什么，哪些可并行，哪些依赖契约或真实接口。
4. 高难任务：先验证哪些未知项，为何保留或继续拆分复杂子任务。
5. 优先级 P0–P3 表示先后，难度 D1–D4 表示挑战程度，分别判断。

## 任务索引

| 编号 | 业务任务组 | 后端工作包 | 前端工作包 | 优先级 |
| --- | --- | --- | --- | --- |
| T01 | [任务组名称](tasks/T01-任务组名称/README.md) | [T01-BE](tasks/T01-任务组名称/backend/README.md) | [T01-FE](tasks/T01-任务组名称/frontend/README.md) | P1 |
```

Single-side work: drop the unused package column or write “不在范围内”; never create an empty
package. Add integration links only when a separate joint acceptance leaf exists.

## Pre-constraints — `00-前置约束.md`

```markdown
# 前置约束

## 目标

1. ...（每条附用户原话或 `file:line` 依据）

## 不做范围

1. ...
2. （用户明确的 Hold / P4 / 明确不做 / 只读 / 禁止项原样写入）

## 边界约束

1. ...
2. 目标环境/分支/部署面：按项目定义写明工作站/测试/生产及双轨选择（如有）。
3. 接口和任务文档格式：Markdown；接口文档是开发、联调、验收基准，默认不使用 Apifox。
4. 前端/后端边界：各自目录、任务编号与允许改动范围；共享契约文档的相对链接。

## 难度与依赖评估

| 业务目标 | 主要难点与当前证据 | 拆分决定 | 前置条件/未知项 |
| --- | --- | --- | --- |
| 当前功能 | 代码、契约或验证路径中的具体复杂点 | 分端结果、D3 继续拆分或保留理由、D4 调研出口 | 上游产物及就绪条件 |

1. 每个叶子任务单独记录优先级、难度和判断依据。
2. 依赖或验证成本变化后，先更新本评估、任务卡与进度表，再继续实施。

## 完成定义

1. `[x]` 需要：代码路径 + 项目门禁 + 目标面上的可达行为（见 `docs/execution-truth.md` §2）。
2. 禁止仅凭能力矩阵、文档勾选或口头「已修好」结案。

## 已知影响范围

1. `path/to/file`

## 最新项目状态

1. 调研时间：YYYY-MM-DD HH:MM。
2. 已确认文件/模块：`path/to/file`
3. 已确认测试/命令：`command`
4. 本计划基于以上状态生成；项目变动后必须回写本文件和进度跟踪表。

## 待确认假设

1. 假设内容 —— 推荐默认：...；依赖它的任务：...

## 验证要求

1. ...

## 阻塞项

1. 无。
```

Finding-sourced work adds 项目定位, 项目口径, 功能角色, 上游 Handoff, Finding 索引 and 修复战役边界 per
[finding-campaign](../../_shared/finding-campaign.md). A short entry may use one bullet per heading.

## Task group — `tasks/T01-任务组名称/README.md`

```markdown
# T01 任务组名称

## 目标

说明这个任务组要解决什么问题。

## 已知范围

1. `path/to/file`

## 工作包索引

| 编号 | 工作包 | 职责 | 依赖与可并行条件 |
| --- | --- | --- | --- |
| T01-BE | [后端](backend/README.md) | 接口行为、权限、业务规则和数据处理 | 契约与项目事实已对齐 |
| T01-FE | [前端](frontend/README.md) | 页面、交互、接口消费和状态呈现 | 链接同一契约，分别说明 UI 开发与真实联调条件 |

## 拆分理由

1. 主要复杂点、各端难度差异、独立验收边界和执行顺序。
2. 仍为 D3 的子任务为何不能继续拆分，或 D4 探索产出如何解锁实现。

## 验收标准

1. 标准一（命令或可观察行为）。
2. 后端和前端分别通过验收；要求跨端闭环时，还需验证真实用户流程。
3. 父级状态从子任务和整体验收汇总，后端完成不代替整个功能完成。
```

## Work package — `backend/README.md`, `frontend/README.md`, or an accurately named package

```markdown
# T01-BE 后端工作包

上级：[T01 任务组名称](../README.md)

## 交付边界

1. 负责的行为、允许改动的目录、调用点及验证面。
2. 不由本端实现的内容和下游交接产物。

## 难度与拆分理由

1. 主要难点及证据：已确认的代码、业务规则、数据风险、未知项和验证成本。
2. 拆分选择：为什么这些结果可以分别验收，哪些改动必须一起保证共同不变量。

## 契约与依赖

1. 共享 Markdown 接口文档及章节的相对链接。
2. 上游任务 ID、所需产物和可开始/可验收条件；无依赖写“无”。
3. 可并行任务及受阻任务的范围。

## 子任务索引

| 子任务 | 优先级 | 难度 | 难度依据 | 依赖与就绪条件 |
| --- | --- | --- | --- | --- |
| [T01-BE-01 后端行为](T01-BE-01-后端行为.md) | P1 | D2 | 本项目的具体复杂点 | 无，或任务 ID + 所需产物/条件 |

## 验收

1. 本端结果的项目门禁与可达行为；执行状态统一查中心进度表和对应任务卡。
```

## Leaf card — one file per leaf

Frontend cards use `FE` IDs and frontend scope; copying one mixed checklist into both sides is not a
split.

````markdown
# T01-BE-01 后端行为

状态：`[ ]`

| 属性 | 内容 |
| --- | --- |
| 上级 | [T01-BE 后端工作包](README.md) |
| 所属端 | 后端（前端任务单独用 FE 编号） |
| 优先级 | P1，写明业务先后依据 |
| 难度 | D2，按当前事实评估 |
| 难度依据 | 具体模块/状态、契约与数据风险、未知项、验证成本；附证据位置 |
| 目标面 | 环境/分支/部署面及双轨选择（项目有多个时必填） |
| 前置依赖 | 任务链接 + 所需产物 + 就绪条件；无依赖写无 |
| 下游影响 | 消费本产物的任务或调用端 |

## 目标

一句话说明本端要完成的独立可验证结果，附需求依据。

## 范围与不做

1. 允许改动的文件、符号与行为；新文件写明已确认的所属模块。
2. 不在范围：另一端实现、无关重构、明确禁区（逐条列出路径或模块）。

## 输入

1. 输入文件或上游任务。
2. 最新项目状态依据：`path/to/file`、`command`、调用点或测试结果。
3. 共享 Markdown 接口契约及具体章节；无需接口时写明原因。

## 上下文检索

<Context-Queries>

```bash
arc-idx files '<已确认的文件片段>' --format json
arc-idx search 'f:<已确认的路径> <已确认的符号或文案>' --context 3 --max 10 --format ai-md
```

</Context-Queries>

交付前把占位命令换成作者已执行并命中目标的精确查询；执行者开工先跑这些命令，再读取和编辑文件。

## 输出

1. 产出文件、清单或代码改动。

## 执行清单

- [ ] 第一步：改哪个文件/符号、为什么这样改、不要改什么。
- [ ] 第二步：要处理的边界条件、错误路径或空状态。
- [ ] 同步：受影响的调用点（点名）。
- [ ] 验证：命令或手工检查与期望结果。

## 不要做

1. 不加兼容垫片或兜底逻辑吞掉错误；不发明领域身份键；不在错误的部署面或轨道上构建、验证。
2. 不只改测试、不放宽断言；不用宽泛重构替代本任务目标；不修改未列入范围的模块。

## 执行注意

1. 完成后同步 `进度跟踪表.md`。
2. 难度或依赖变化时重新拆分并回写；D4 探索任务写清待验证问题、证据产物和退出条件。

## 完成标准

1. 本端代码路径、项目门禁和目标面可达行为；列出命令/操作及期望结果。
2. 进度跟踪表已更新命令和结果。
3. 要求真实接口联调时，Mock 通过后仍为 `[?]`；后端通过不代替前端验收。
````

## Progress tracker — `进度跟踪表.md`

Columns in this order; difficulty reasons live in the cards; every leaf is a row, parents are not.

```markdown
# 进度跟踪表

| 状态 | 编号 | 所属端 | 优先级 | 难度 | 子任务 | 上级 | 依赖/就绪条件 | 下一步 | 完成说明 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `[ ]` | T01-BE-01 | 后端 | P1 | D2 | [后端行为](tasks/T01-任务组名称/backend/T01-BE-01-后端行为.md) | T01-BE | 无或已确认的上游条件 | 下一步动作 |  |
| `[ ]` | T01-FE-01 | 前端 | P1 | D1 | [前端行为](tasks/T01-任务组名称/frontend/T01-FE-01-前端行为.md) | T01-FE | T01-BE-01：契约已对齐可做 UI；真实接口可达后验收联调 | 下一步动作 |  |
```
