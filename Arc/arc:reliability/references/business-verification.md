# 业务规则到验证场景

在选择测试工具之前读本页。目标是定义什么叫正确，以及什么执行能够推翻“它正确”的判断。

## 从当前变更反推业务合同

复用已有需求、API/领域合同与历史事故记录。记录变化涉及的角色与权限、合法状态迁移、输入边界、计数/配额、时间点、持久化结果、事件和外部副作用。追踪哪些其他入口/任务能观察或改变同一状态，决定回归范围。

先写失败后果、暴露机会、影响范围、发现/恢复难度，再选场景。明确本次必需项、已有证据、未测内容与原因；不要将测试层级或主观总分当成优先级。配置、数据与运维工具的变更也要纳入影响分析。范围和专业用例设计见 [`arc:test 用例设计`](../../arc:test/references/test-case-design.md)。

身份、角色、来源、租户和状态值来自项目事实。例子中的 `A`、`B`、`X` 只是示意，不作为项目种子或默认 ID。

分别表达：

- **Safety / 安全性**：任何时候都不能发生的结果，例如数量不能为负、一次逻辑操作不能重复扣款。
- **Liveness / 活性**：在明确条件和项目给定时限内应完成的进展，例如依赖恢复后待处理事件被处理或进入可见失败状态。

“最终一致”必须有完成条件、观察窗口和超时后的契约；不替项目发明固定秒数。处理超时或查询失败不是“未发生副作用”的证据。

## 适用维度

只展开影响本次规则的维度。不适用写原因即可，不造空表格；是否适用未知时记缺口。

| 维度 | 会改变验证决策的事实 |
|---|---|
| 状态与权限 | 合法/禁止迁移、终态、撤销后语义；未授权操作不得留下持久变化 |
| 并发与重试 | 共享资源、检查后写入、操作身份、重复/镜像参数、未知提交结果 |
| 外部副作用与异步 | 事务与外部效果的边界、重复/乱序投递、部分成功、补偿/对账 |
| 时间与长期运行 | 过期边界、时钟来源、取消、排队/资源增长、恢复时限 |
| 兼容、迁移与破坏性 | 旧数据/旧客户端/混合版本、迁移中断、回滚支持范围与数据恢复 |

对适用维度分别看正常运行、发生故障、恢复过程和版本/配置变化。阶段有各自的失败模型；不能用一次正常成功替代其余阶段，也不要求普通小改动全覆盖。

## 每个重要场景的最小规格

| 字段 | 必须能回答 |
|---|---|
| Rule / source | 哪条项目规则，本次变化为何影响它，错了有什么后果 |
| Preconditions / action | 什么状态与数据，谁通过哪个业务入口执行哪些动作 |
| EXPECTED | 持久化终态、计数、事件/外部效果与后续任务必须怎样 |
| FORBIDDEN | 重复/丢失效果、越权、错误对象/数量、非法迁移等哪些结果不得出现 |
| Oracle | `kind + observe + assertion`：从哪里独立观察，用什么确切断言判正确 |
| Sensitivity | 哪种现实缺陷应让本例失败，哪个断言会发现；必要的反例检查及未验证限制 |
| Evidence binding | 项目现有命令/测试选择器或人工步骤、真实依赖、证据位置、是否为本次必需项 |

**弱判定**：“取消请求返回 200”。

**业务判定示例**：若项目合同规定取消需释放占用，则最终实体进入规定状态，占用只释放一次，同一逻辑取消的重试不重复产生效果；相关事件/退款/审计仅按项目实际合同检查，未定义时记 `SPECIFICATION GAP`。不能把示例中的退款或候补规则当作所有系统的默认业务。

判定尽量不调用被测实现的同一个算法来计算期望值。用简单独立模型、真实数据库终态、事件/审计、设备读数或对账视图；mock 的调用次数仅能证明调用契约，不能证明远端最终效果。

同时比较正确对象、完整集合/内容和禁止副作用。终态正确不证明过程中没有违反不变量，需要时检查操作历史与中间语义点。判定器无法读取状态或执行零次检查不能解释成“未发生错误”。完整推演见 [`库存、支付通知与取消示例`](worked-example.md)。

## 选择能证伪当前主张的最小技术

| 规则或失败形态 | 首选证据 |
|---|---|
| 确定性规则、阈值、多条件策略 | 示例/边界、等价类、决策表 |
| 状态流转、策略优化、大输入空间 | 状态模型、独立参考/差分、属性测试 |
| 解析/协议/文件 | fuzz + 有语义断言的 corpus，保留失败输入 |
| 数据库隔离、锁与跨业务竞争 | 真实应用路径 + 真实数据库 + 可控交错 |
| 重试、未知结果、异步副作用 | 按边界注入故障 + 幂等/终态/对账断言 |
| 迁移、重启与恢复 | 代表性旧数据和生命周期验证，比较不变量 |
| 过载、长时间资源行为 | 负载/soak + 不变量 + 队列/泄漏/恢复观测，性能单独判定 |

大组合按业务后果、频率、共享状态、事故历史、可逆性和可检测性排序。pairwise 可减少组合，但不能删掉已知危险的三方交互。随机输入必须有 oracle，记录 seed/schedule/corpus；压力碰撞不能替代可确定重放的关键竞态。

生成器也需要审查：数据是否过度相关，只命中连续记录或方便构造的状态；断言是否只看数量、复用被测算法。对关键新断言或历史回归，条件允许时用原故障版/有界负例确认它会因目标缺陷失败。不要为每次低风险修改强制全套变异测试。

形式化模型、系统模拟、Loom/调度探索只用于足够关键且可建模的边界。模型通过表示在其假设下未找到反例，不能宣称真实系统无缺陷。

## 分离规格、绑定和当前状态

业务规则/稳定场景 ID 随合同维护；实现重构只更新测试/执行绑定。绑定至少能定位真实测试选择器、工作目录、前置条件、操作和判定；一个没有断言的脚本退出 0 不构成业务通过。

人工场景需要可复现步骤、实际观察、操作者和时间；分析场景需要明确模型/假设与结论。两者不得冒充已执行的自动化或真实依赖验证。执行状态和门禁规则见 [`evidence-and-release.md`](evidence-and-release.md)。
