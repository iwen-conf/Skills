# 检测、恢复与事故学习

用于业务不变量的生产检测、服务可靠性取舍或事故防复发。若正在处理故障，`arc:fix` 先按 [`Evidence-first root-cause repair`](../../../docs/execution-truth.md#6-evidence-first-root-cause-repair) 确认问题和根因，本页补充控制闭环。

## 用户结果与服务指标

用项目现有 SLI/SLO、统计窗口、排除条件和负责人。没有时提出可评审的定义与缺失数据，不能擅定 99.9%、延迟或恢复时限。

可用性/延迟 SLI 应能映射到用户完成任务的结果；平均值可能掩盖失败群体和尾延迟。异步业务还应看队列年龄、重试放大、积压与完成时间。错误预算只能管理服务可用性取舍，不能“预算化”重复扣款、数据损坏或权限泄露。

对于关键规则，回答：测试漏掉后怎样观察违反、何时发现、谁处理、怎样停止扩大、能否对账/修复。按现有架构选择有业务意义的非法迁移计数、重复效果检测、对账差异、审计/状态版本或合成探针；没有明确行动的指标不自动变成告警。

## 遏制与恢复

发布前按风险确认分阶段范围、与基线比较的业务指标、停止条件和实际可用的恢复路径。应用回滚不能自动撤销数据库迁移或外部副作用；需要明确前滚、补偿、人工修复或备份恢复的适用条件。

恢复要求至少区分恢复时间目标 RTO 与允许丢失的数据窗口 RPO，数值来自项目。备份“成功生成”不证明可恢复：在已授权隔离环境恢复后执行真实业务查询/对账，并记录耗时、数据完整性和可重新提供服务的证据。

故障/恢复演练先写稳态假设、最小影响范围、故障操作、观测器、截止/停止条件和恢复步骤。使用已授权环境；生产 chaos 永远不作为默认取证手段。不能为了演练突破只读或禁止重启。

应急通路也是验证对象：回滚工具、配置分发、对账/恢复工具、凭据和控制台是否会依赖正在失效的服务。必要时在隔离演练中验证实际操作与效果，不只检查 runbook 文件存在。

## 验证升级、配置与支持的回退范围

旧版与新版分别通过，不证明两者能在一次滚动发布中共存。涉及格式、协议、状态、schema 或开关时，用代表性旧数据和持续业务流验证过渡过程。

| 阶段 | 观察 |
|---|---|
| 准备 / 能力兼容 | 所有相关读者、消费者和后台任务已具备新格式能力；不能只凭大部分实例健康就激活新写入 |
| 旧新共存 | 按真实部署顺序运行写入/读取、回调和任务；持续检查业务不变量与错误归属 |
| 全部升级 / 激活 | 新写入与旧数据并存，后台作业和异步周期被覆盖；有效配置与预期一致 |
| 回退 / 恢复 | 退到项目明确支持的版本后仍能处理已写数据和事件，业务不变量与进展仍成立 |

Prepare/Activate 是一种可选设计，不是所有项目的强制发布模式。激活新格式后可能只能退回已兼容读取的版本，不能假定能回到最初版本；删除旧格式读取能力前必须有旧数据已迁移的证据。上线/回退由已有运维流程执行，本技能不自行部署。

## 金丝雀观察必须具有代表性

发布验证已有授权时，选能反映用户结果的指标和群体：成功/错误、尾延迟、业务不变量、异步任务年龄与完成结果。窗口需覆盖相关流量、工作单元和后台周期；低流量下少数成功请求或健康检查不足以通过，缺失样本是证据不足。

优先比较同时间、可比条件下的候选与对照，并能按版本/配置/群体归因。仅看变更前后可能混入流量和时间变化；共享数据库、缓存或队列又可能让候选拖累对照。因此同时看绝对业务要求/SLO，并记录共享影响面与观测器健康，不能只因两组一样差而通过。

合成流量和流量复制不覆盖所有生产状态；复制写请求还可能产生重复副作用或改变缓存/负载。使用隔离和项目允许的流量方式，保留这些限制。金丝雀是补充证据，不替代缺失的提交前必需验证，也不自动授权生产实验。

## 事故形成持久控制

1. **固定事实。** 保存版本/环境、触发条件、时间线与用户影响，区分已观察事实和待证假设；尽可能保留最小复现、输入、seed 或交错。
2. **落到不变量。** 与 `arc:fix` 确认架构归属、违反的业务规则、根因和同类路径；解释既有验证为什么漏掉，不以“加重试”代替根因。
3. **选择控制。** 根据证据补预防（约束/修复）、检测（断言/对账）、遏制（边界/暂停）或恢复（补偿/重放）；只添加实际需要的控制。
4. **验证能抓住已知失败。** 用保留的最小复现或安全的故障模型证明新增测试/检测确实会发现原问题，再验证修复后通过。无法重放时记录替代证据的局限，不能宣称已经复现。
5. **纳入日常执行。** 回归进入相应 CI 周期；告警与恢复有负责人和可执行步骤。需长期跟踪则交 `arc:sdlc`，任务关联规则、证据和精确 `<Context-Queries>`；有飞书项目再经 `arc:docs` 同步。

复盘完成不等于整改完成。未执行控制验证时保持 `NOT_RUN/BLOCKED` 或 `[?]`；控制可实现时不能只有复盘文档。

## 吸收来源与适配

学习用户提供的 `reliability-engineering-skill` v3：业务规格/执行绑定/环境契约/证据分离、EXPECTED/FORBIDDEN、独立 oracle、真实事务与跨业务并发、可重放故障、逐场景门禁及事故控制闭环。

在 Arc 内复用 `arc:idx` 检索、`arc:test` 原生测试、`arc:fix` 根因门禁与 `arc:sdlc` 任务分级。来源自带 TOML/Python 编排器未成为依赖；环境改为远端 Docker/PostgreSQL，任务/API 文档沿用 Markdown，测试配置使用分环境的隐藏 JSON。既有 CI 即可承载绑定和证据，只有项目存在真实缺口时才实现最小适配。

本轮已核读的一手资料、公司实践差异和适用限制集中在 [`industry-testing-strategies.md`](industry-testing-strategies.md)：包括 Google 测试计划/SRE/金丝雀、AWS 回退安全、Netflix FIT、Uber BITS、FoundationDB、SQLite、TigerBeetle、Cloudflare 事故及测试专家方法。本文的升级与金丝雀检查是对其中 AWS、Google 实践的适配。

原来源保留的事务背景阅读：[PostgreSQL 锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)、[AWS 幂等 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)、[Jepsen 一致性模型](https://jepsen.io/consistency/models)。使用时仍以项目实际版本/配置和实测证据为准，不假定所有系统具有相同语义。
