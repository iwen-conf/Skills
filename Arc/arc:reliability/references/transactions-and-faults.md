# 事务、并发与故障验证

业务操作是并发验证单元。先读真实入口、调用者和事务封装，再推导交错；表名或锁序清单只是线索。

## 事务与副作用清单

按实际受影响业务操作记录：事务起止、隔离级别、读写行/索引范围/谓词、锁与实体取得顺序、事务内网络调用、超时/重试所有者、幂等键及保留/重复语义、outbox/inbox、热点和事务时长预算。预算来自项目；缺失则列为待确定。

每项连到提交、回滚、重试和恢复后必须成立的不变量。幂等需要区分同一身份同一参数、同一身份不同参数、并发重复、过期/清理后的重放，以及身份的租户/业务作用域；具体行为以合同为准。

## 竞争矩阵

| 组合 | 需要观察 |
|---|---|
| 同操作重复：`cancel(X) || cancel(X)` | 状态只转换一次、计数与外部效果不重复 |
| 同操作镜像：`transfer(A,B) || transfer(B,A)` | 多实体锁是否按稳定规范顺序取得，非按请求方向 |
| 重叠批量：同一实体集合的不同排列/子集 | 索引范围和逐项锁顺序、原子性、部分结果 |
| 不同操作共享状态：取消/回调、退款/结算、过期/审批 | 哪个动作赢由合同决定，另一方结果和终态一致 |
| 高风险三方组合：用户/操作员/定时任务 | 两两通过后仍可能出现的共享不变量破坏 |

案例仅在项目存在相应业务时使用。先覆盖受本次变化影响的共享边界，再按证据扩大。

## 强制关键交错

优先通过真实应用 API/job/usecase 和生产使用的事务/ORM 层，对真实依赖执行；SQL 缩小复现用于理解数据库语义，不能代替应用重试和副作用链的证明。

在“读到余额之后”“第一把锁已持有”“提交前”等语义点使用显式 barrier/failpoint。同步必须有超时、取消/清理和可重放顺序，避免测试自身永久挂住。复用现有测试接缝；新接缝通过测试装配或依赖注入进入，不能增加绕过业务规则的生产 `var` 开关。禁止用 sleep 猜测时序。

barrier 必须在真实锁/事务语义下可达，不能让持锁方等待一个必须取得同一把锁才能到达的参与者。区分应用竞态与测试自己制造的死等；保留调度和锁证据。

并发历史记录调用、完成/超时、操作身份、结果和观察终态。超时表示结果未知，不能自动当作回滚。判定器依据项目承诺的一致性模型检查历史；只在请求成功返回的子集上检查会漏掉未知结果的副作用。

## PostgreSQL 语义

| 观察/故障 | 取证和验证 |
|---|---|
| `40001` 序列化失败 | 在新事务内重跑完整业务尝试，重读状态；验证最终不变量 |
| `40P01` 死锁 | 保存实际锁/等待与语句路径，确认系统性锁序反转；重试不替代根因修复 |
| 等待与尾延迟 | 可用时观察 `pg_stat_activity`、`pg_locks`、`pg_blocking_pids()`，按运行/应用/测试标识限定采集范围 |
| 提交结果未知 | 通过持久化状态、幂等记录或对账确认效果，不能盲目再发副作用 |
| 热点与重试放大 | 看成功/失败/重试耗尽、锁等待、事务 p95/p99、idle-in-transaction 与终态校验 |

真实锁可能来自 FK、触发器、upsert、索引、谓词、执行计划和动态键顺序。静态锁序无环不能证明无死锁；Go `-race` 通过也不能证明数据库业务并发安全。

重试由明确的一层负责，遵守最大尝试/总截止时间、退避与取消；多层相乘会造成放大。重试完整业务事务，但不能无条件重放已发生的支付/通知等外部效果；验证项目的幂等、outbox、补偿或对账语义，不强行引入新模式。

本机不启动 PostgreSQL。使用用户指定的远端已有测试实例/CI 隔离环境；网络经 SSH tunnel 或服务器 CLI。没有环境时先形成可运行绑定与准确前置条件，状态为 `BLOCKED`，不能以 mock 结果补成真实数据库 `PASS`。

## 故障点从边界推导

| 边界 | 代表性故障点与断言 |
|---|---|
| DB → 消息/外部 API | 提交前失败、提交后响应丢失、发送成功但确认丢失；检查丢失/重复与可恢复状态 |
| 消费/异步任务 | 重复、乱序、延迟、毒消息、处理后确认前崩溃；检查重入与最终归宿 |
| 超时/取消 | 客户端取消与服务器完成竞速；截止时间传播、资源释放和可查询终态 |
| 网络/资源 | reset、依赖慢、连接池/队列耗尽；检查背压、重试放大和恢复后的进展 |
| 持久化/迁移 | 写入中断、进程重启、旧数据/混合版本；检查恢复、不变量及支持的回退范围 |

先写假设、操作范围、观测和停止条件，再进行已授权的最小故障实验。若必须依赖锁观察器或对账器才能作判断，它不可用或采集失败就是证据缺口；不能因主测试进程退出 0 宣布通过。

恢复测试须同时证明故障期间的安全性和恢复后的有界进展。性能与正确性分开报告：高 TPS 伴随错误状态仍是失败。环境和证据门禁见 [`evidence-and-release.md`](evidence-and-release.md)。

整体健康或多数节点能服务，不代表每个受影响任务、分片或副本都能恢复。按项目承诺检查局部进展与可见失败归宿。恢复路径本身存在高风险时，补恢复期间再次发生 I/O、资源或依赖故障的场景；先确认条件和期望，不能无边界叠加 chaos。
