# 用例设计示例：库存预占、支付通知与取消

本页演示如何从合同得到测试范围、场景、断言和执行要求。**以下是特意定义的示例合同，不是当前项目事实。** 状态名、操作名、标识和策略都必须替换为项目已有合同；不可复制成默认业务规则或种子。

## 示例合同与范围

系统只有预占、确认和取消三种库存操作；本例没有补货、发货出库或退货。支付通知表示外部已发生的付款，本系统不在回调中再次收费。

| 规则 | 本例已明确的承诺 |
|---|---|
| R1 库存 | 对数量 `q`，只允许整数 `1 ≤ q ≤ Qmax` 且可用库存足够；预占成功减少可用量并建立 `HELD`，不能超卖 |
| R2 状态 | `HELD → CONFIRMED` 保留库存占用；`HELD → CANCELLED` 释放一次；确认与取消竞速由先成功提交的合法迁移决定，已确认后取消拒绝 |
| R3 重复 | 同一操作身份、相同参数重复执行返回一致的业务结果，不重复改变库存或履约效果；相同身份不同参数拒绝 |
| R4 通知 | 确认后产生履约事件；消息可以重复投递，最终履约接受记录按预占身份恰好一份。已取消后收到付款通知只记录唯一的待对账事项，库存保持释放 |
| R5 权限与进展 | 用户只能操作自己的预占；可信支付入口按合同验证来源。依赖健康、worker 可运行且没有新故障时，已确认业务应在项目规定的 `D` 内形成履约接受记录 |

`Qmax`、`D`、请求重试截止时间和目标环境必须由实际项目提供，示例不赋默认数值。真实支付结算、退款、发货和对账事项最终处置不在本例范围；不能据此宣称完整交易系统已可靠。

在本例封闭范围内，库存不变量为：

```text
available + sum(quantity of HELD) + sum(quantity of CONFIRMED) = initial_stock
available >= 0
quantity / owner / reservation identity 与合同一致
每个 CONFIRMED 最终恰好一份履约接受记录；CANCELLED 没有履约接受记录
```

最后一项包含有条件、有截止时间的活性要求，不能把事件尚未完成投递时的暂时缺失立即判为错误。任何时刻的禁止副作用仍须检查，不能等它被“修回去”后只看终态。

## 为什么这些风险进入必需范围

假设本次变更同时涉及库存条件更新、回调去重和 worker 重试。变更会影响共享库存与履约：超卖/重复效果后果重，超时后用户会重试，worker 崩溃窗口真实存在，错误可能直到对账才出现。因此对应规则是本次必需项。

若真实变更只有帮助文案，此范围不适用。测试范围必须跟随变更和合同，不因示例列了五组场景就全部照跑。

| 场景组 | 前置条件与动作 | 必需的强断言 | 执行边界 |
|---|---|---|---|
| S1 边界与拒绝 | `q` 为零、边界内/外、恰好可用量/超过可用量；跨用户操作；相同操作身份改参数 | 合法输入的精确结果；拒绝后目标和其他用户的库存、预占、履约记录不变。允许的拒绝审计按合同另查 | 决策表小测试 + 真实入口的代表性持久化检查 |
| S2 最后一份库存 | 两个不同预占同时竞争 `initial_stock=1, q=1`，制造可解释的交错 | 恰好一个成功、另一个库存不足；只有正确身份的 `HELD`；可用量为零且守恒。未强制胜者时不能预指定某用户必胜 | 真实 usecase/事务与真实数据库；记录两个操作的历史 |
| S3 状态竞速与重复 | 并发重复取消、重复确认；确认先提交/取消先提交两种顺序；已取消后付款通知重放 | 确认赢：不释放、唯一履约效果，取消拒绝。取消赢：释放一次、无履约、唯一待对账事项。重复传输不等于重复业务效果 | 可控交错 + 状态/库存/事件/履约精确核对 |
| S4 未知结果与恢复 | DB 提交后响应丢失，同身份重试；worker 写入履约后、确认消息前崩溃，再恢复并重投 | 不因客户端超时推断回滚；预占和业务效果各一份；恢复后在 `D` 内进展，不吞掉待处理项，不重复收费 | 真实持久化/消息语义 + 定点故障 + 恢复后的独立查询 |
| S5 兼容变化（适用时） | 若本次同时改变状态/事件格式或去重身份：旧新版本共存、全量新版本、回退到支持版本，持续处理旧新数据 | 各阶段 R1–R5 不变；旧消费者/后台任务能处理支持格式；回退后仍可读取已写数据 | 代表性部署拓扑、真实历史数据和后台工作周期 |

S5 只有涉及兼容风险才纳入；它不会因为属于“升级测试”就自动降为可选。性能风险存在时另设负载与资源预算证据，功能场景通过不代替容量结论。

## 展开 S4：消息重投为什么不会重复履约

**要发现的缺陷：** 消费者在确认消息前已产生效果，崩溃重投后再次执行效果。仅断言消费者被调用或队列最终为空，均无法发现它。

1. **准备。** 在已授权的隔离环境创建一个本例合法预占，记录其身份与库存基线，完成确认。确认真实 worker、消息确认模式与去重约束；观察器能独立读取履约接受记录。清理仅限本次数据。
2. **控制故障。** 在“履约效果已持久化、消息尚未确认”的语义点使本次 worker 停止；记录效果提交证据与消息身份。故障接缝必须匹配真实系统机制，不能用 mock 调用计数冒充该窗口。
3. **恢复和重投。** 恢复 worker，让消息按真实投递机制再次到达；复用同一逻辑事件身份。记录每次投递、处理结果、确认和终态，等待业务完成条件直到合同截止时间，不用固定 sleep。
4. **独立判断。** 查询完整的履约接受记录集合，确认它只包含当前预占的正确对象/数量，且恰好一份；其他预占没有新增效果。核对库存守恒、状态仍为确认、没有额外收费请求，消息最终完成或按合同进入可见终态。观察器失败则无法判定。
5. **验证敏感性。** 若存在历史重复执行缺陷，先用原故障版和同一场景观察断言失败，再验证修复版。没有历史版本且风险值得时，可在隔离副本用有界负例检查去重断言；未做这项检查应如实记录。

真实系统若把效果落在外部服务，必须通过该服务的测试接口/对账观察效果；本地“已发送”字段不能证明远端只执行一次。环境不具备观察能力时，该主张为 `BLOCKED`，可以继续验证其他独立规则。

## 对照：看起来绿与能够发现错误

| 弱判定 | 可漏掉的错误 | 本例采用的判定 |
|---|---|---|
| 请求返回成功 | 写错对象、未落库、后续任务丢失 | 身份、数量、状态、库存与履约结果完整核对 |
| 履约记录有一条 | 一条记录属于其他预占 | 精确集合及字段比较，同时检查禁止影响的对象 |
| 两次重试都成功 | 重复释放或重复效果 | 同一逻辑身份的效果唯一且守恒 |
| worker 重启后健康 | 某条任务永远卡住，整体仍返回成功 | 当前任务在规定条件与期限内完成，积压与失败去向可解释 |
| 新旧版本分别通过 | 混合部署期间格式不兼容 | 持续业务流中的共存、升级、支持范围内的回退证据 |

## 交给执行者的证据要求

通过 `arc-idx` 找到项目真实测试选择器、入口、事务层、消息适配器、CI 和 fixtures 后，再把上面的场景组绑定到 `arc:test`。这里没有项目代码或环境，**所有示例均是设计示范，状态为 `NOT_RUN`**，不能复制成已通过的测试报告。

每次实际运行保存：场景与规则、候选/配置/环境身份、具体选择器与工具版本、受控交错/故障位置、操作历史、完整业务观察、失败及清理制品。示例卡格式见 [`change-verification.md`](change-verification.md)，状态和阻断规则见 [`evidence-and-release.md`](evidence-and-release.md)。
