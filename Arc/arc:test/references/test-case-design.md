# 从业务风险设计测试范围与用例

用于决定测什么、在哪一层测、怎样判断结果，以及现有测试为何会漏掉缺陷。测试的价值是减少对业务能否正常运行的不确定性；用例数量、执行次数和覆盖率只描述其中一部分。

## 先形成范围，再选择工具

从当前合同和变更出发，沿真实入口、调用者、共享数据和依赖画出最小影响面。不要只按修改文件或函数清单选测试；配置、运行参数、数据迁移和运维工具也能改变行为。复用已有测试计划，普通任务用短卡即可。

| 范围问题 | 要留下的决策 |
|---|---|
| 谁的什么承诺可能失效 | 用户任务、业务规则及来源，允许/禁止结果，损失或影响 |
| 哪些条件会触发 | 状态、角色、数据分布、调用顺序、依赖、配置、版本、时间与负载 |
| 为什么优先验证 | 后果、真实暴露机会、共享影响面、历史事故、发现及恢复难度；区分事实与假设 |
| 用什么证据回答 | 最小可信测试边界、独立判定依据、实际部署形态、可执行选择器 |
| 这次不回答什么 | 明确不测/暂缓项、已有替代证据、残余风险和重新纳入的触发条件 |

用项目优先级约定排序，不把几个主观分数相乘后当作发布结论。分别标记**本次必需项**与执行周期；优先级不是测试类型，成本高也不是自动延期的理由。先执行能最大程度减少关键不确定性的场景。

需求存在决定性歧义时列 `SPECIFICATION GAP`；只询问缺失的业务决定，继续可独立完成的范围、数据和绑定工作。不要将实现当前的输出倒推成需求。

## 四个阶段决定系统测试范围

| 阶段 | 适用时应检验的承诺 |
|---|---|
| 正常运行 | 核心任务、边界/空状态、权限、真实数据分布、可接受延迟与容量 |
| 发生故障 | 慢依赖、超时/取消、重复/乱序、部分提交、资源耗尽下的安全性与失败语义 |
| 恢复过程 | 重启、依赖恢复、重放/补偿、积压消退、备份恢复；没有丢失/重复，受影响任务能继续前进 |
| 发生变化 | 配置/开关、旧数据、混合版本、升级/回滚、迁移中断、后台任务与运维操作 |

按风险选择各阶段，不要求每次小改动全跑。正常返回不证明故障可控；进程恢复健康不证明积压、数据和业务都恢复。每个阶段都要有自己的观察和退出条件。

## 用例是一条可被推翻的业务主张

| 字段 | 内容 |
|---|---|
| Claim / risk | 规则来源、失败后果、它是否是本次必需项 |
| Preconditions | 可复现的状态、数据、权限、版本/配置与真实依赖 |
| Actions / history | 通过哪个入口、按什么顺序执行；竞态的交错、故障位置与恢复动作 |
| EXPECTED / FORBIDDEN | 精确结果、持久化变化、事件/外部效果；必须没有的变化 |
| Oracle | 期望从何而来、如何独立观察；安全性与有条件、有时限的活性分别判定 |
| Sensitivity | 哪种现实缺陷应使本用例失败，哪个断言会发现它 |
| Binding / evidence | 实际测试选择器/命令、数据准备与清理、观察器、失败制品；未执行保持 `NOT_RUN` |

给定–动作–结果结构可以帮助表达，但不能省略副作用和故障后的结果。API `200`、不抛异常、mock 调用次数或记录条数通常只证明局部事实。

## 按风险选择设计方法

| 风险结构 | 用例设计方式 | 容易漏掉的部分 |
|---|---|---|
| 输入范围、数量、时间阈值 | 等价类 + 边界值；有效、无效、缺失、空值、边界两侧 | 单位、精度、时区/时钟来源、上限恰好值与溢出 |
| 多条件规则与权限 | 决策表；每个条件独立改变决策的对照；允许与拒绝两侧 | 全部条件同真/同假，测不到单个条件是否生效 |
| 有状态业务 | 状态迁移/操作序列；合法和禁止迁移、重复操作、终态后的请求 | 测过每个状态却没测迁移顺序，中间态产生过禁止副作用 |
| 并发、重试、部分成功 | 操作历史 + 可控交错 + 故障点；未知结果后的查询与重放 | 只测成功响应、只做压力碰撞、只检查最终计数 |
| 大输入或组合空间 | 属性、独立模型/差分、fuzz；按约束抽样或组合覆盖 | 生成器相关性、不可达状态、oracle 与实现共用错误逻辑 |

组合测试保留已知危险的三方或更多交互；pairwise 不是高阶交互已验证的证明。对顺序敏感的业务还要覆盖历史，参数取值两两覆盖不能代替操作顺序。精确复现关键路径，再用生成式测试探索未知路径。

属性只采用合同成立的性质。例如两个操作可交换、编码解码能无损往返、重复调用无副作用，都需要先确认适用条件。差分测试也要先对齐规格、精度、排序与允许差异，不能把另一实现当成绝对真理。

## 选择能承载该语义的边界

纯规则优先小测试；持久化、锁、隔离、驱动或消息确认语义要有真实边界的集成证据；跨服务/终端关键任务需要能够观察完整业务效果的验收场景。测试边界由架构和主张决定，不规定 E2E 占比，也不重复在每一层测试所有输入组合。

一个完整服务集成测试可能比很多高度 mock 的单元测试更直接；一个纯函数的决策表也可能比庞大的 E2E 更准确。写清哪些依赖替换了、替换隐藏了什么风险。工具选择和范围视图见 [`test-scope-matrix.md`](test-scope-matrix.md)。

运行约束沿用当前任务和 Arc：本机不为测试启动 PostgreSQL 或容器运行时。真实环境不足时完成能执行的部分，真实依赖证据记 `BLOCKED`。

## 检查判定器本身

1. **来源独立。** 先用当前业务合同、独立简化模型、人工推导的具体结果或可信对账定义期望。不要调用被测算法计算期望；共享格式解析可以复用，但被验证的业务判断不能循环证明自己。
2. **结果足够精确。** 检查对象身份、完整集合/内容、金额/数量、顺序（合同要求时）、状态以及禁止副作用。两个错误列表可能长度相同；测试“有一条记录”不能证明写对了记录。
3. **观察覆盖时间。** 最终状态正确不能证明过程中从未超卖或越权。需要时检查操作历史、事务约束、事件/审计和中间语义点。异步等待使用业务完成条件、项目截止时间和超时证据，不能 sleep 后碰运气。
4. **失败可被看见。** 观察器连接失败、权限不足、数据延迟或检查零次都不能解释为“未发现错误”。针对关键主张核对一个已知反例能否触发相应断言。
5. **冲突公开。** 历史版本、同类产品和文档都可能错误；发现 oracle 不一致先记录差异与依据，不能挑最容易通过的那个，也不能自动把疑点认定为产品缺陷。

## 验证测试确实对缺陷敏感

问清：“如果去掉去重、反转边界判断、少发一个事件、遗漏一个结果，这个用例在哪里失败？”无法回答时先改善场景或断言，增加相似用例通常无益。

对关键新断言或历史回归，有条件时用**修复前版本的最小复现**、隔离测试副本中的有界变异，或已知错误的判定器输入验证其敏感性，再验证正确版本通过。记录反例、预期失败的断言及实际结果。因编译失败或测试环境损坏而红灯，不算抓到了该业务缺陷。

变异不是每次修改的必做项，更不是新的分数指标。等价变异、与当前合同无关的变异和仅影响性能的变异要分类；功能断言不一定能捕获性能退化。不得修改共享/生产目标来证明测试有效，也不得留下绕过业务规则的生产开关。

确认是测试或判定器缺陷后可以修正测试，并保留证据；不能为适应产品的错误行为改期望。产品缺陷按 `arc:fix` 的根因门禁处理。

## 生成器与探索性测试

生成器需要审查**到达过什么业务状态**，不只统计随机次数：独立和相关字段、稀疏/密集数据、命中/不命中、相等/不同、热点/冷数据、重复/唯一键、少见和极端分布。约束只排除业务确实不允许的组合，不为了方便判定而排除真实输入。

例如交集查询的数据若总把匹配记录连续放在两个索引中，就可能永远不触发跳跃扫描；应构造不相关键、稀疏交集与交错插入，并比较完整结果集合。fuzz 可以同时检查崩溃和业务性质；属性测试描述判定性质，两者能够结合。

保存失败 seed、输入、历史/调度和工具版本；缩小反例时确认失败原因仍相同。随机 seed 在真实并发环境中未必足以重放调度。

对规格不完整、交互复杂或历史风险区域，可安排有时限的探索：明确要探索的风险、数据与环境，记录操作和发现，再把可复现的重要失败转成回归。探索性发现是线索，仍须核对合同和根因。

## 结束条件

当约定的必需主张已有当前版本的有效证据、项目门禁通过、残余风险和未测范围明确时结束。新变更、失败或未解决风险才触发扩展；不因覆盖率尚能上涨继续堆测试。
