# Static SQL Checks

Parsers and linters judge SQL text; they never prove a query returns the right rows. Let the
tools report first, then judge findings in context. Result correctness stays with oracles
([case-design.md](case-design.md), db mode G4).

## 1. Layers

| Layer | Tool | Proves | Does not prove |
|---|---|---|---|
| Parse in the dialect | SQLFluff `lint --dialect <d>`: codes `PRS` (parse), `LXR` (lex), `TMP` (template) | the text is valid in that dialect's grammar | that tables, columns and types exist; SQLFluff's grammar can lag new engine syntax, so confirm a suspect `PRS` with the engine itself (`EXPLAIN`) |
| Rules | SQLFluff rules the project selects, e.g. `AM04` (`SELECT *`), `CP01` (keyword case), `RF` references, `ST` structure | the team's conventions | correctness; findings are advisory unless the project gates them |
| Schema binding | `EXPLAIN` without `ANALYZE` of each statement on the migrated test database; PostgreSQL 16+ `EXPLAIN (GENERIC_PLAN)` accepts `$1` parameters | names and types resolve on the real schema; the plan shape | results (property tests, G4) |
| Migration lock safety (PostgreSQL) | Squawk, e.g. `require-concurrent-index-creation`, `require-lock-timeout`, `prefer-robust-stmts` | the migration avoids blocking locks it does not need | duration and locks on real data (G18 rehearsal) |

## 2. Where each runs

- Implementation: `gate.sh check` runs `lint(sql)` on changed `.sql` files under the project's
  sqlfluff config (`.sqlfluff`, `[tool.sqlfluff]`, `[sqlfluff]` in `setup.cfg`/`tox.ini`), and
  Squawk when `.squawk.toml` exists. No config → `NOT_RUN`: the dialect is a project decision.
- Release qualification: `[sql_static]` in the dbqual config
  (`examples/sql-static.example.toml.fragment`) runs `sql_static_audit.py` inside run_suite and
  writes run-bound evidence `sql.static`; require it in the gate policy with `{"id": "sql.static"}`.
- SQL embedded in application strings or generated by an ORM is invisible to file linters. Bind
  it to the schema through the real data-access layer in integration tests or the query gate
  (`[[query]]` EXPLAIN); for ORM output, capture the statements from the test run
  (`log_statement`, `pg_stat_statements`) and EXPLAIN those.

## 3. Rules

- The dialect and the gating rules come from project config (`.sqlfluff` rules, `fail_on`);
  never invent a style policy. Parse, lex and template errors always fail: a file the tool could
  not read cannot pass.
- Templated SQL (dbt, Jinja) needs the project's templater settings; a `TMP` error is either a
  template bug or missing context, and both block.
- Every Squawk finding on a migration blocks unless the config excludes that rule with a written
  rationale (`[sql_static.squawk_excluded_rules]`); speed is not a rationale.
- `sqlfluff fix` rewrites files: only inside `arc:code` with the diff reviewed, never here.
- Pin tool versions in CI (`sqlfluff_command`, `squawk_command`) and keep the versions in evidence.

## 4. Verdicts

| Observation | Verdict |
|---|---|
| Every file in scope parsed, no gating rule hit, no unexcluded Squawk finding | `PASS` for "these files, this dialect, these rules" only |
| Parse, lex or template error; gating rule hit; Squawk finding | `FAIL` with `file:line` and code |
| Tool missing, usage error, glob matched nothing, a file absent from the report, no dialect | `BLOCKED` (the implementation gate reports a missing config as `NOT_RUN`) |
| Advisory findings only | `PASS` with the counts listed as warnings |
