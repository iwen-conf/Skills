# HTTP API 设计合理性审查

来源：用户要求「检查 HTTP API 设计的合理性，去网上搜索规定，上传、JSON 字段限制等，需要评估设计缺陷」，并决定加入已有技能还是新增技能。

目标：审查既有或拟议 API 的协议语义、字段合同、资源限额、上传生命周期、授权及兼容性，输出有权威依据和反证检查的缺陷；不以格式正确或文档齐全代替设计正确。

采用现有 Arc：`arc:audit` 增加 `api-design` 模式；共享 API 规则由 `arc:plan`、`arc:code`、`arc:verify` 按阶段使用，不新增顶层技能或重复审查权威。TypeSafe 本回合 `jev ask` 对此归属返回 `noul = 0.83`，仅作语义辅助。

验收：

- 每条规则区分标准要求、安全建议、项目合同、工具/部署事实，带官方 URL、章节和适用版本；遇到变化或未覆盖问题继续网上核验。
- 明确 required/null/空值、字符与字节、数值精度、未知字段、重复键、数组与嵌套限制；不虚构统一上传大小或字段长度。
- 上传覆盖解析前资源控制、内容验证、临时对象与完成确认、授权和清理；不把文件名/MIME/schema 当安全证明。
- 设计缺陷、实现缺陷、规格缺口、运行时未验证分别报告；给出反例、影响、修复归属和验收用例。
- 保持只读评审边界；新增参考在本机完整安装包可达，既有技能与未提交改动保留。

不做：为具体业务发明字段、限额或权限，不对外部 API 扫描、上传测试文件或压测，不新增通用扫描器，不变更 API 文档格式政策。
