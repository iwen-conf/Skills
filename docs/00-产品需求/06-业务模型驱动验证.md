# 业务模型驱动验证

2026-10-30 用户裁决：业务能力、业务行为、测试验证分层；六视图读取统一模型，形成可导航、可追踪、可执行、可验证的工作台。继续强化现有六个 Arc 技能、Go CLI 与项目本地 Turso。此文记录要求，不代表验收通过。

来源：完整《自动化测试规范设计》对话、[PR #1](https://github.com/iwen-conf/Skills/pull/1)、本轮附件 `pasted-text-1.txt`（SHA-256 `5dde97989b81f5374bdec6a2bee33c3408969ed730340d84803eda265f492ae3`）。附件中的“本轮只评估”是历史回复；当前要求是实现完整体系。

| BG03 | 业务规则、条件、状态、不变量、测试定义与每次执行分开 | 每个测试有条件、动作、预期、Oracle、恢复；历史 FAIL 不被重试覆盖 |
| BG04 | 六视图：全景、能力、边界、流程、验证、影响；三空间：建模、验证、分析 | 同节点跨视图保持身份；领域→能力→流程→测试→证据逐层下钻 |
| BG05 | 按领域、角色、完整度、验证状态过滤；版本、环境、轮次可选择 | 只选择账本实际存在的上下文；筛选/分页不改变完整覆盖分母 |
| BG06 | 边界表示规则、数据、能力所有权与跨边界契约；部署边界单独表达 | 冲突所有权和循环依赖有诊断；显式合法共享有理由；进程不充当业务边界 |
| BG07 | 从已声明合同生成正向、条件负向、强制、流转和不变量义务，支持明确边界/并发/幂等/恢复场景 | 未实现、未规划、未执行、未知可达、缺证据均不变成 PASS |
| BG08 | 检查条件组合可达性，有界探索状态、步数、路径及时间 | 模型不可达有约束依据；预算耗尽明确 truncated/UNKNOWN；有限证明范围单列 |
| BG09 | 不变量有可执行独立判据与观察边界 | 读取独立事实并执行比较；缺测量、错误 Oracle 或反例不能通过 |
| BG10 | 能力只有完整必需规则、分支、不变量、恢复义务具备当前有效证据才点绿 | 四维覆盖与逐项门禁一致；BLOCKED/NOT_RUN/FLAKY/陈旧不算通过 |
| BG11 | 绿、部分、失败、未验证、阻塞、待复验来自真实证据 | 全图 gate 未满足不能直接把节点涂红；旧 FAIL 与当前状态分别可见 |
| BG12 | 输入变更传播到受影响能力与测试；缺口与完整度分析 | 差异按稳定 ID；影响只走明确定义的依赖/规则/验证传播关系 |
| BG13 | 回放实际步骤、条件、expected/observed、首个偏离和 RAW/hash | 逐步/暂停/首个偏离不改账本，不生成未执行路径 |
| BG14 | 执行接既有真实入口、独立 Oracle 与身份绑定 | graph/task/run、候选、环境、目标、主体、账号、fixture、配置、轮次一致 |
| BG15 | fixture 恢复包含隔离范围、动作日志、独立状态读回与安全继续检查 | 外部副作用不能靠数据库 rollback 名称消失；恢复失败保留原 FAIL 并阻止复用 |
| BG16 | 小店首讯/排队/领取、主动联系与审批介入、群发/recall/离线链三卡先接通，再逐族补齐 39 族 | 真实合同/版本和隔离范围绑定；旧发现或 API ACK 不冒充真实端送达 |
| BG17 | 六技能由要求、规则、图、任务、证据、修复、复验形成交接闭环 | 每阶段只执行其职责；FAIL 修复后独立复验，模型通过不代替业务通过 |
| BG18 | arc-policy 正确区分会话归属和完成声明，仍要求真实门禁 | 安装包真实 hook 检查只读并发、缺 Post、否定/引用、实际写入与无回执提交 |
| BG19 | 补齐对话定下的三类义务：EXISTENCE（规则声明必须存在的功能）、SEQUENCE（多步业务链按顺序整体验证）、CONSISTENCY（同一操作在页面、API、数据库、异步结果各层由独立 Oracle 读到一致） | 三类义务进入完整分母；缺实现证据的 EXISTENCE 只成候选缺口，扩大检索并经用户确认后才判 MISSING；SEQUENCE 中途偏离保留首个偏离；任一层缺观察为 BLOCKED，不是 PASS |
| BG20 | 业务验收报告与业务风险报告分开；RISK 状态区分 OPEN、ACCEPTED_RISK（带范围与决策记录）、已升级为 RULE | 风险数不进缺陷数；接受风险必须写明范围和用户原话；风险审查门禁只在项目配置要求时生效，不默认阻止验收 |
| BG21 | 业务状态等价判定：只在影响后续行为的属性（状态、条件取值、主体/角色、模型声明的历史敏感属性）都相同时合并 | 未声明等价依据的状态不合并；合并记录依据；被合并路径可追溯；探索、去重和派生义务都复用同一判定 |
| BG22 | 已知路径由确定性执行器连续推进，只在未知状态、前提不满足、偏离或新分支出现时停下交给 AI | 连续执行仍逐步留 RAW 和独立判定；停下时给出最小上下文包（当前状态、偏离步、候选动作）；总时限和步数有上限 |
| BG23 | 任务卡自动繁殖：执行中观察到的偏离或异常，按规则派生新的验证义务并挂回原节点 | 派生义务按 BG21 去重，有数量预算和风险排序；原 FAIL 和原任务含义不变；派生义务来源于 RULE 才是验收义务，来源于推断只是 RISK 探索 |
| BG24 | 未知业务探索：DISCOVERY 任务像用户一样操作，记录契约外的行为为 UNSPECIFIED | UNSPECIFIED 不判 PASS/FAIL；由用户分流为遗漏需求、允许的扩展或不应存在；探索有预算，结果带证据并按 BG21 去重 |
| BG25 | 工作台是 CLI 一次性导出的静态只读快照（HTML+JSON），浏览器直接打开 | 不起服务、不发网络请求；页面没有执行、批准、导入、重试入口；快照记录生成时间、图版本 hash、环境、轮次和导出时重验过的证据 hash |
| BG26 | 业务语义按三种来源分开：用户/文档要求（RULE）、代码实际实现的行为（实现证据）、同类系统参照（RISK）；三者两两比对 | 实现证据永远不能变成 RULE；要求有而实现无 → 候选缺口（BG19 EXISTENCE）；实现有而要求无 → UNSPECIFIED（BG24）；参照有而要求无 → RISK 候选；每条结论标明来源类别 |
| BG27 | AI 或参照来源的 RISK 在交给用户前做一次有界反证：找"产品有意如此"的证据和支持它的真实行为观察 | 反证结果（支持、反对、未找到）和证据随 RISK 保存；没做反证标"未反证"；反证结果不改变它的 RISK 身份 |
| BG28 | 同类系统不变量参照库：按领域保存可复用的不变量模板，每条带来源和适用条件 | 只能生成 RISK 候选；适用条件不满足就不生成；来源缺失的模板拒绝导入 |
| BG29 | 测量 Verify 自身的检出能力：在一次性副本里给试点系统注入代表性业务逻辑缺陷，跑生成的义务，报告检出与漏检清单 | 缺陷类别至少覆盖越权、竞态/超卖、非法状态转移、幂等破坏、缺服务端校验；结果只报告、不设通用阈值门禁；注入版本只部署到已授权的隔离环境 |
| BG30 | AI 产生的候选（RISK、UNSPECIFIED、派生义务）按来源类别记录用户分流结果，统计接受/驳回/待定 | 在风险报告里展示；只用于改进，不作门禁；样本不足时如实标注 |
| BG31 | API 级状态化探索工具（首选 Schemathesis）作为 runner 适配器的候选，先做开源选型再决定 | 选型记录先于任何依赖引入；未选定前 W09 只登记外部探索结果 |

借鉴结论：粘贴文本的总判断成立——已有局部成果，没有能可靠审计任意业务系统的成熟方案。这与 Verify 现有原则一致：用户定义正确性，AI 只提候选，独立 Oracle 和真实执行定结论。据此新增 BG26–BG31：

- 三种来源分开（对应文中"三件事不能混淆"）；
- 风险先反证（文中"找到足以推翻它们的证据"；LogiAgent 约三分之一判断不准）；
- 参照不变量库（LogicScan 的对照思路，只产生 RISK）；
- 用注入缺陷测量检出率（LLM-SID 的 BLV-Bench 做法，回答"凭什么确信"）；
- 分流精度台账；
- Schemathesis 选型。

已有设计已覆盖、无需新增的：AI 提出的边界/所有权只作诊断候选（BG06），探索有预算（BG08、BG24）。
