# 全量已安装技能架构评审

- 日期：2026-10-08
- 状态：已于 2026-10-08 实施（T08），实施记录与偏离见附录 D
- 范围：本机 5 个宿主（Claude Code、Codex、Gemini、Grok、Pi）能发现的全部技能，以及 `~/.agents/skills` 中未链接到任何宿主的副本，共 162 个唯一技能目录、204 份磁盘副本；外加两份全局指令 `~/.codex/AGENTS.md`、`~/.claude/CLAUDE.md`。
- 前序：Arc 内部的 16 → 5 重构见 [01 ARC 技能架构重构评审](01-ARC技能架构重构评审.md)，已于 2026-10-05 实施，随后新增 `arc:closure` 成为第 6 个。本文不重复该文已定的结论（如 `arc-idx version` 精确身份校验是用户在 ca82692 中有意恢复的，不再讨论），只评审实施后的现状和 Arc 以外的全部家族。

评审方法与口径：

- 清单由脚本从各宿主技能目录解析 frontmatter 生成，统计 SKILL.md 正文、references 与 description 的 token。Token 按"ASCII 字符 ÷ 4 + 中日韩字符 × 1"估算，与前序评审同口径，误差约 ±15%，只用于相对比较。
- 重叠度是评审估计：A 的规范性条目中，能在 B 找到语义等价表述的比例。凡标"估计"的数字都不是工具测量值。
- 路由混淆用 TypeSafe Jev（`jev-1.13.0`，`jev ask` Choice）模拟：输入用户请求，以已安装技能的真实 description 作选项。它模拟的是"仅凭 description 选技能"这一步，不等于宿主真实路由器的行为。原始结果见附录 B。
- 未验证：各宿主真实路由行为；Codex / Gemini 是否递归发现嵌套的 SKILL.md；各技能的真实使用频率（本机没有使用遥测）。因此安装分层只是建议的默认值，最终启用哪些由你决定。

## 0. 结论摘要

现在的问题不在 Arc 内部，而在 Arc 之外：

1. **全局指令把任务路由到已经不存在的技能。** 每个会话都会常驻加载 `~/.codex/AGENTS.md`，它提到 14 个已退役的 Arc 名称（`arc:sdlc`、`arc:idx`、`arc:build`、`arc:fix`、`arc:test`、`arc:prewalk`、`arc-dbqual` 等），当前 6 个技能里只提到 `arc:audit` 一个。它要求读取的 `~/.agents/skills/arc-dbqual/SKILL.md` 也已不存在。
2. **装得太多，Claude 的技能清单已经溢出。** Claude 宿主能发现 100 个技能，本会话注入的技能清单里有 22 个只剩名字、没有 description，其中包括全局规则要求强制使用的 `typesafe-ai`，以及 `read`、`write`、`testing-setup` 这类歧义很大的名字。
3. **第三方技能劫持 Arc 的路由。** Jev 模拟显示：普通的"做落地页"有 0.93 的概率走 `taste-skill`（它默认 Next.js + Phosphor 图标，Arc 前端规范默认 Vite + TanStack + shadcn）；一般的 PR 评审在 `cnb-code-review`（0.52）和 `arc-audit`（0.48）之间几乎对半；"修 bug 并提交 PR"有 0.89 走 `cnb-code-commit`；"查过度设计"有 0.99 走 `ponytail-audit`。
4. **动作级碎片化集中在第三方家族。** Three.js 有 25 个技能、CNB 14 个、UI 审美 15 个、ponytail 6 个、Lazycat 5 个、agent-browser 6 个，全都是一个领域拆成多个动作。
5. **Arc 的技能数降了，单任务加载量却回到了重构前的水平。** 修一个 Go 缺陷要加载约 18.1K token（重构前 17.3K，预算 10.9K）。原因是共享文档在膨胀，以及 `arc:closure` 带进来的 `workflow.md` 被全部 6 个技能列为必读。

方案：按"常驻核心 + 领域路由 + 不可发现的库"三层重组。

| 指标 | 现在 | 方案后（预算） |
|---|---:|---:|
| 唯一技能目录 | 162（磁盘副本 204） | 22（每个只有 1 份真源） |
| Claude 可发现技能 | 100 | 9 个常驻 + 按 profile 启用的领域路由（work 13 个，mobile 16 个） |
| Codex 可发现技能 | 127 | 约 13–20 |
| Claude 每会话 description 常驻量 | 8.7K | 约 2.3K |
| 全局指令常驻量 | 6.6K | ≤2K |
| 一个领域任务需要加载的技能数 | 1–3（Lark 2、learn 3、perfetto 2、lazycat 迁移链 3） | 1 个主技能 + 1 份库条目或 reference |

能力方面：只删除营销展示（`ponytail-gain`）、帮助卡（`ponytail-help`）、测试夹具、重定向空壳和失效副本；其余内容都有明确去向（附录 A）。新增 4 项能力：跨家族路由回归、安装治理检查、设计到代码的交接合同（DESIGN.md）、场景级加载预算门禁。

### 1.2 结构性问题

1. **全局指令过期，而且是最高优先级的上下文。** 统计 `~/.codex/AGENTS.md` 与 `~/.claude/CLAUDE.md` 中的 Arc 名称：退役名 `sdlc` 4 次、`idx` 4 次、`arc-dbqual` 3 次，`test`、`fix`、`clarify`、`build` 各 2 次，`security`、`prewalk`、`frontend`、`docs`、`define`、`comment`、`arch` 各 1 次；当前名 `explore`、`plan`、`code`、`verify`、`closure` 0 次。它要求的 `<Context-Queries>` 现在由 `arc:plan/references/task-docs.md` 承接，文中却仍写成 `arc:sdlc`。
2. **安装面没有治理。**
   - 33 个技能名在磁盘上有 2–3 份不同内容的副本。例如 `android-intent-security` 的正文，`~/.agents` 版约 0.5K，`~/.gemini` 版约 5.6K；`cloudflare` 的正文，`~/.agents` 版约 5.9K，`~/.codex` 版约 2.0K。
   - 19 个孤儿副本没有链接到任何宿主。
   - Claude 与 Codex 中各有 1 个失效链接 `OfficeCLI`。
   - 测试夹具 `good-skill`、`good-skill-complex`、`good-skill-minimal`、`lark-demo`（2026-09-01 安装，来源不在本仓）被当作正式技能加载。
   - 17 个技能的目录名与 frontmatter `name` 不一致（如 `taste-skill` → `design-taste-frontend`、`lazycat:ship-app` → `lazycat-ship-app`）。
3. **发现预算溢出。** 本会话的 Claude 技能清单中，以下 22 个只剩名字：learn、migrate-xml-views-to-jetpack-compose、navigation-3、perfetto-sql、perfetto-trace-analysis、play-billing-library-version-upgrade、ponytail-debt、ponytail-gain、ponytail-review、r8-analyzer、read、redesign-skill、soft-skill、stitch-skill、styles、taste-skill、taste-skill-v1、testing-setup、typesafe-ai、verified-email、wear-compose-m3、write。被截掉的基本是按字母序排在 lark / lazycat 之后的技能；Lark 一个家族就占了 Claude description 常驻量的 40%（3,470 / 8,702）。
4. **只有 Arc 有路由回归。** `schemas/trigger_corpus.yaml` 只覆盖 6 个 Arc 技能，其余 156 个技能与 Arc 之间从来没有测过近似负例。1.3 节的 4 处劫持都发生在 Arc 与非 Arc 之间。
5. **领域被拆成动作。** 用户提供的反例（search / symbol-search / ast-search ……）在 Arc 内部已经消除，但在第三方家族里大量存在。最典型的是 Three.js：`core-math`、`core-raycaster`、`syntax-materials`、`impl-shadows`、`errors-rendering` 等 25 个，都属于同一个领域。
6. **一个任务同时加载多个技能。**
   - 25 个 Lark SKILL.md 引用 `lark-shared`（共 51 处，如 lark-calendar 正文开头就要求"开始前先读"），17 个带 CRITICAL 块。
   - `learn` 在 metadata 中声明依赖 `read`、`write`。
   - `perfetto-trace-analysis` 依赖 `perfetto-sql`。
   - Lazycat 的迁移链 license → boundary → ship 是 3 个技能。
   - `cnb-pr-summary` 先要调用 `cnb-pr-diff`。
7. **第三方规则与本仓规范直接冲突。**
   - `taste-skill` §3 默认 Next.js RSC、Tailwind v4、Motion、Phosphor 图标，并"不鼓励 lucide-react"；`Arc/_shared/conventions/frontend.md` 默认 React 19 + Vite + TanStack Router + shadcn/ui，而 shadcn 默认使用 lucide。

### 1.6 最大能力缺口

1. **没有跨家族路由验证**（直接导致 1.3 节的劫持）。

### M1. arc:closure → arc:plan（新增 `model` 模式）

```text
arc:plan(prd / brief / tasks / layout / campaign) + arc:closure(design / change / audit / gate)
↓
arc:plan(prd / brief / model / tasks / layout / campaign)
```

- **权限与产物相同。** closure 只写文档、spec 和工件，产物是"可检查的规格"；按前序评审 §10.1 第 1 条，它不满足独立条件。
- **消除两棵文档树。** `docs/arc/` 并入 `docs/00–11`：spec 放 `docs/01-系统设计/closure-spec.yaml`，业务设计并入同目录，漏洞登记并入任务文档。旧项目的 `docs/arc/` 继续可读，不批量迁移。
- **`workflow.md` 不再是 6 个技能的第 0 步必读。** 闭环闸门只在 model 模式和"实现已建模行为"时读取，arc:code 只在 Intent Router 命中"已有 closure spec"时读。
- **路由验证。**
  - 合并后，"订单状态流转有没有漏洞"走 arc:plan 0.98、"设计退款状态机"走 arc:plan 1.0、"体检"和"支付越权审计"走 arc:audit 1.0。
  - 前提是业务漏洞审查必须整体归 plan，arc:audit 的 description 明确把"状态机漏洞 / 闭环检查"指向 plan。
  - 反例：两边都写"业务漏洞"时，分布是 0.53 / 0.47，置信 0.30。
- **收益**：少 1 个入口；每个 Arc 任务少读 `workflow.md` 1.9K；需求只有一个权威位置。

### 6.2 arc:plan（吸收 closure 后）

- **description（新）**："Turns intent into written specs and checkable models without touching source code: PRD (写PRD, 需求文档), brief with acceptance criteria (需求澄清, 验收标准), business closure models — design a new lifecycle or check an existing flow for dead ends, missing compensation or illegal transitions (业务闭环, 状态机, 状态流转漏洞, 事件联动, 异常恢复, 闭环检查) with the closure checker, task breakdown and progress (拆任务, 任务文档, 进度跟踪), audit findings into task batches. Not for implementation (arc:code) or code review (arc:audit)."
- **Intent Router 新增**：

  | Condition | Mode | Read |
  |---|---|---|
  | 生命周期、状态机、事件联动、异常恢复的设计或修改 | model | `references/model.md`（原 design-workflow + spec-format） |

### 6.3 领域路由模板（lark、android、cloudflare 共用）

**用途**：上游维护、条目多、单个任务只用其中一两项的家族。路由器是自有文件；上游正文原样放进库里，不改。

**目录形态**：

```text
<family>/                 # 唯一可发现的 SKILL.md
├── SKILL.md              # ≤2K：认证/前置一次写清 + 路由表 + 通用失败处理
└── library/<entry>/      # 上游原文；打包时把 SKILL.md 改名为 ENTRY.md，宿主不会发现
    ├── ENTRY.md
    └── references/…
```

**路由器 SKILL.md 必含**：

- **Trigger**：写在 description 里。家族名、中英文产品名，以及 URL 或 token 模式（例如 Lark 的 `/docx/`、`/wiki/`、`/sheets/`、`/base/` 路径，以及 doubao.com 等价路径）。
- **Non-trigger**：该家族以外的相邻场景，并写明去向（例如 Lark 的"本地 PRD → arc:plan"）。
- **Goal**：选中唯一一个库条目并完成任务；每次写入都附平台返回的标识。
- **Inputs**：用户意图，以及可选的 URL / token、身份（user / bot）。
- **Workflow**：
  1. 执行一次前置：Lark 是 `lark-cli auth status`，Android 是 `android` CLI 可用性检查。
  2. 按路由表选 1 个条目，然后读 `library/<entry>/ENTRY.md`。
  3. 按条目说明执行。
  4. 核对平台返回的标识或状态。
  5. 按"完成 / 部分 / 失败 / 阻塞"汇报。
- **Tool Strategy**：首选家族 CLI；遇到 CLI 未封装的接口，走库中的 openapi-explorer 条目；禁止猜 token。
- **Decision Rules**：
  - URL 路径决定条目，域名不决定；
  - 一个请求涉及两个条目时，按"读 → 写"的顺序依次读取，每次只读 1 个条目；
  - 别名表负责旧名映射（例如 lark-minutes → meeting）。
- **Verification**：每个写操作都有平台返回的 ID；只读操作注明来源。
- **Failure Recovery**：
  - 认证失败：执行 `auth login` 一次，仍失败则报告；
  - 条目没命中：先读路由表的"相邻条目"列，再报告缺口；
  - 平台返回错误码：按条目的错误表处理，同一错误重试最多 1 次。
- **Completion Criteria**：条目已选定；所有写入都有标识；未完成项附原因。

**打包要求**：`sync_skills.py` 新增 `--library` 目标，校验每个宿主只发现路由器。

**按家族的取舍**：

| 家族 | 路由器正文 | 库条目 | 特别处理 |
|---|---|---|---|
| lark | ≤2K：吸收 lark-shared 的认证与身份规则 | 24 个上游 + project-docs（自有，`.lark.json` 合同不变） | 4 个空壳进别名表；Arc contract §7 的飞书钩子改为 `lark`（project-docs） |
| android | ≤1.5K：android CLI、平台默认值（指向 native-platforms.md） | 19 个 | perfetto-sql 与 trace-analysis 在路由表中作为一组；本仓对 android-cli、verified-email 的本地改动收回到路由器，库里保持上游原文 |
| cloudflare | 已有伞形 SKILL.md，改造即可 | 伞形 references + 并入的 13 个 | 每次引用数字前先查官方文档（上游已有此要求，保留） |

### 6.4 ui-design

- **Trigger**：视觉方向、风格、设计规范、去 AI 味审美、改版审计、页面参考图、品牌视觉板。
- **Non-trigger**：
  - 写或改页面代码 → arc:code（frontend）；
  - 交互逻辑和状态 → arc:code；
  - 蓝湖设计稿读取 → lanhu-design。
- **Goal**：产出 `DESIGN.md`，可选附参考图。arc:code 拿到后，不需要再做任何审美决策就能实现。
- **Inputs**：产品与受众（必填）；风格预设（可选，默认由 brief 推断）；现有站点或截图（audit 模式必填）。
- **Workflow**：
  1. 用 3 行写出产品、受众、气质。
  2. 选 1 个预设（读对应 reference）。
  3. audit 模式：按 AI 痕迹清单逐条标注现有 UI 的问题。
  4. 写 `DESIGN.md` 的 7 节：主题、色板与角色、字体层级、组件样式、布局、动效、禁用模式。
  5. reference-images 模式：每个区块单独生成 1 张参考图。
  6. 自检：每条规则都是可实现的数值或可判定的禁令。
- **Tool Strategy**：
  - 不写 HTML、CSS 或组件代码；
  - 不指定框架或图标库，由 frontend.md 决定；
  - 色值用 token 名加数值。
- **Decision Rules**：
  - 用户点名风格时，按点名选预设，不再推断；
  - 预设与项目已有设计系统冲突时，保留现有系统，只给增量。
- **Verification**：DESIGN.md 的 7 节齐全；禁用模式可以用代码扫描检查（例如禁止 `h-screen`，使用 `min-h-[100dvh]`）。
- **Failure Recovery**：brief 缺受众时问 1 个问题，同时给出默认值；生图失败时只交付 DESIGN.md，并说明缺图。
- **Completion Criteria**：DESIGN.md 已写入项目根目录或 docs；交接给 arc:code 的那一行已写明。

### 6.5 research-write

- **Trigger**：读或抓取 URL / PDF、联网检索、多源研究成稿、中英文润色、去 AI 味、本地化。
- **Non-trigger**：
  - 仓内文件 → 直接读；
  - 代码注释 → arc:code；
  - 提交信息 → check；
  - 飞书文档 → lark。
- **模式**：fetch / search / research / edit。research 按需调用 fetch 与 search，都在同一个技能内完成。
- **Verification**：
  - fetch：来源 URL 与抓取层级；
  - research：每个论断都有来源，矛盾单独列出；
  - edit：标点门禁脚本通过。
- **Failure Recovery**：直连失败时，只有在用户授权后才走第三方提取；检索为空时换关键词最多 2 次，然后报告。

### 6.6 check

- 原有内容保留，范围扩大到任意 git 宿主：GitHub 走 `gh`，CNB 走 `cnb`（pulls create 与 comment）。
- 吸收 cnb-code-commit 的分支与 PR 安全步骤：
  - 记录 `git status` 基线；
  - 不自动 stash；
  - base 分支按"用户指定 → PR 真实 base → 默认分支"的顺序解析；
  - 已有 PR 时，核对 head 与 base 后再推送。
- description 写明："只在代码改动已完成后使用；仍需改代码 → arc:code"。
  - 模拟中，"修报错并提交开 PR"仍在 check 0.69 / arc:code 0.31 之间分流，置信 0.53。
  - 这是两阶段请求，走到任一边都能交接，但需要语料覆盖。
- 可选：改名为 `deliver`，避免"check / 检查"在只显示名字时被误路由。

### 6.7 cnb、harmonyos、lazycat、threejs

都按 6.3 的结构写：Trigger 和 Non-trigger 写在 description 里；正文是一张模式表、一次前置、各模式 1 份 reference，失败恢复用表格。要点：

- cnb 的 description 必须写"仅限 CNB 平台"；review 模式输出行级评论之前，先展示发现并确认授权（沿用 cnb-runtime 的"加载技能不等于授权发布"）。
- harmonyos 的 docs-lookup 步骤：在凭记忆回答 API、权限、生命周期问题之前，先查本地官方文档索引（原 official-docs 的黄金路径）。
- lazycat 的模式门禁顺序固定：intake 通过才能进 boundary，boundary 通过或完成 POC 才能进 ship；original 直接进 ship；update 独立。每个模式沿用原技能的"允许 / 禁止"表。
- threejs 正文不放 API 表，只放"症状 → reference"的路由表和全局 anti-pattern。

2. 每个技能只有一份磁盘真源，宿主一律使用 symlink。`sync --check` 发现实体目录副本时失败。
3. 目录名必须等于 frontmatter `name`。新技能禁止使用单个通用词作名字（core、read、write、check、styles、setup）。
4. 每个宿主的 description 总量 ≤3K token。超出时先削减 L2，不得截断 L1。验证方法：宿主技能清单中没有只显示名字的条目。

### 10.2 什么时候新增独立技能

在前序评审 §10.1 四条之外，再加两条：

5. 用 Jev 探针对它和所有相邻技能（包括非 Arc 技能）各跑至少 3 条近似负例，top-1 置信都 ≥0.8。
6. 如果它属于已有领域，只能成为该领域路由的库条目或模式，不能新开入口。

### 10.3 上游与第三方

- 上游内容原样放进 library，本地改动只写在自有路由器或 conventions 里。本仓 Android 对 android-cli、verified-email 的改动要按此收回。
- CLI 自己能按版本下发技能内容时（agent-browser），只安装桩。
- 第三方技能装进 L1 或 L2 之前，必须先做冲突检查：技术栈默认值、检索工具、常驻人格、"ACTIVE EVERY RESPONSE"类指令，都与 Arc 规范逐项对照，有冲突就不能直接装。
- 许可证随包保留。

### 10.4 Token

- 新增场景级预算：每个 L1 技能列出 3–5 个典型场景，单场景总加载量 ≤13K，由校验器计算。
- 正文不写 Trigger 节，触发词只写在 description。
- 同一条规则只在一个文件里写全文，其他位置只写 1 行指针；全局指令只放指针。
- 删除测试（前序 §10.4）同样适用于第三方内容：模型本来就懂的 API 速查表要删除。

### 10.5 工作流与验证

- 跨阶段交接只走 handoff 记录，不要求每个技能开头都读交接协议。
- 两阶段请求（修复并提交、审计并修复）在语料中单独标注，断言的是首阶段技能。
- 路由类判断按全局 TypeSafe 规则走 `jev ask`，并在报告中写出概率与置信。
