## 对比结论

| 维度 | security-audit 强项 | arc:audit 原有强项 |
|---|---|---|
| 判定门槛 | 每个候选必须写清低信任主体、输入、本应生效的控制、被跨越的边界、受影响对象和具体结果；同主体/自伤、缺最佳实践不算发现 | 状态词表（confirmed/likely/needs-triage/false-positive/manual-gap）与反证检查 |
| 方法 | 从具体不变量出发；对比兄弟路径的控制是否等价；边界输入清单；高危发现后找变体；深度上限 | 资产清单优先、数据产出（L0–L4）排序、先打配置/密钥/调试面与边缘模块 |
| 攻击类别 | 9 个通用类 + 10 个领域补充（HTTP 与身份、浏览器、数据隔离与生命周期、供应链与 CI、云与部署、协议/RPC/消息、资源耗尽、桌面/移动/IPC、内存安全、AI/LLM/Agent） | 以 Web/业务为主的软目标队列，覆盖支付回调、短信轰炸等本地常见场景 |
| 严重度 | 只有已确认记录才有严重度；高/中判别：是否完全击穿一个显式控制 | 数据产出驱动的严重度与工具严重度重排规则 |
| 覆盖 | 确定性覆盖台账（入口 × 边界 × 子系统 × 类别）与状态表；历史报告沿用规则；限定范围必须声明部分覆盖 | `coverage.md` 粗粒度清单 |
| 执行安全 | 运行目标代码只在无网络、空环境、只读目标、有资源上限的沙箱内，否则不执行 | 全程只读，主动检测必须有书面授权（scan 模式 DAST） |
| 工具与交接 | `findings.json` + JSON Schema + Node 校验器；多代理预算与产物提升流程 | `security-scan.py`（Semgrep、Trivy、gitleaks 等）、发现转任务（finding-campaign）、合同词表与优先级映射 |

## 有意不吸收

- `findings.json`、`report-schema.json`、`validate-*.cjs`：引入 Node 校验链与第二套词表；Arc 用 Markdown 发现卡和合同 §4 词表。
- 多代理预算、波次与 race-safe 产物提升流程：Arc 以单代理为主，子代理规则在合同 §6；需要时再评估。
- 输出目录放到仓库外：Arc 统一写 `.arc/artifacts/<slug>/`，默认不提交。
- guidance / full 双模式：arc:audit 每次都产出报告与覆盖表。

## 上游更新后的复核流程

1. 查上游最新提交：`gh api 'repos/cloudflare/security-audit-skill/commits?per_page=1' --jq '.[0] | {sha, date: .commit.committer.date}'`。
2. 与固定提交不同时看变更文件：`gh api repos/cloudflare/security-audit-skill/compare/c1c8a8c1471069fb0e188eeaff69b8e8db6564a8...<新提交> --jq '.files[] | "\(.status) \(.filename)"'`。
3. 逐个变更判断：吸收进上表落点，或记入“有意不吸收”并写原因；改写为 Arc 的表述，不整段复制。
4. 更新 `appsec.md`、`attack-classes.md` 与本文的固定提交；许可证变化时同步替换 `upstream/security-audit-LICENSE`。
5. 运行 `.venv/bin/python scripts/validate_skills.py` 与 `uv run --no-sync python -m pytest -q`，再按 `Arc/README.md` 安装。
