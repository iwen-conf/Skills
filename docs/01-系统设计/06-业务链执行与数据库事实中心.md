## 2. 整改核心验收标准

任意一次真实执行结束后，仅凭本地 `.arc/arc.db`（及关联查询命令 `arc verify explain` / `trace` / 静态快照）必须能够针对图上任意已声明的业务节点或执行步骤，无歧义回答以下 6 个问题，并支持按真实后态延续下一步：

1. **谁在执行、操作什么对象**：参与角色、账号别名、Principal、会话状态、关联业务实体（如订单 `P`、退款 `R`、通知 `N`）及其来源步骤与归属关系。
2. **为什么允许或拒绝**：区分"环境/目标夹具准备条件"与"本场景受测业务条件"，给出每个条件的声明对象、期望布尔值、从哪个 Oracle 指针读到的真实属性值和最终比较结果。
3. **实际做了什么**：动作节点、转移边、目标入口、经过模板注入后的真实请求摘要与响应状态/摘要（脱敏后）。
4. **期待与实际发生了什么**：预期目标状态或 `UNCHANGED`、异步等待轨迹（若适用）、各观察层前后快照、每条业务断言与不变量的逐项输入及判定。
5. **为何判 PASS / FAIL / BLOCKED**：每条断言的 `PASS/FAIL/BLOCKED` 明细；保留首次偏离步与原始 `FAIL`，后续恢复或重跑不覆盖原失败。
6. **能否及如何继续下一步**：实体绑定在旅程内连续传递，只在整条 `SEQUENCE` 旅程结束时统一恢复；意外失败后通过独立 Oracle 核清实际后态，安全则建立关联延续分支，状态未知则停写取证。

## 3. 详细技术设计

### 3.1 R1：跨能力连续旅程与结构化前置条件（`model_v2.go`）

1. **跨能力 `BehaviorFlow`**：
   - 保留 `BehaviorFlow.Capability`（主归属能力，保持向后兼容），新增可选字段 `Capabilities []string`（`json:"capabilities,omitempty"`）。
   - `validateBusinessModel` 校验 `Capabilities` 中每项均为已声明 `capability` 节点。
   - `validateSequence` 判定某步 `contract.Action` 是否被允许时，放行"属于 `flow.Capability` **或** 属于 `flow.Capabilities` 任一能力"的动作，使一条 `SEQUENCE` 可以真实跨越 `CAP-PAY → CAP-CALLBACK → CAP-DELIVERY → CAP-REFUND → CAP-LOOKUP`。
   - `modelObligations` 对 `SEQUENCE` 的 `Targets` 同步纳入 `flow.Capabilities` 与每步实际触达的 `capability` 节点，确保能力树覆盖统计不漏计。
2. **规则与不变量的规范 Oracle 标识**：
   - `Rule.Oracle` 与 `BusinessInvariant.Oracle` 作为机器可执行标识（如 `ORA-PG-AND-MOCK`），人类可读说明保留在 `Rule.Description` / `NodeContract.Description`。
   - 保持对已有 v1/v2 模型的兼容（校验器不因旧图含中文 oracle 字符串而拒绝读取旧账本）。
3. **结构化前置条件主体说明（可选增强字段）**：
   - 在 `Rule` / `TransitionContract` 上保持 `Conditions []string` 与 `ConditionAssignment`（`map[string]bool`）作为严格判定核心，新增可选元数据 `ConditionSubjects []ConditionSubject`（`{Condition, SubjectKind, SubjectAlias, Attribute, Operator, Expected, Description}`），用于在 `next` / `explain` / 快照中精确展示"作用于哪个参与者或实体的哪个属性"。
   - 运行时执行器在 `execute.go` 明确区分：
     - `setup` 隔离基线与夹具可用性检查失败 → 一律判 `BLOCKED`（不记为产品业务 `FAIL`）；
     - 场景声明条件（含 `NEGATIVE` 用例故意构造的 `false` 条件）按 `observedConditions(actual, expected, required)` 核验，先确认目标否定条件真的处于 `false` 再发出请求，避免"条件没布置好却误测通过"。

### 3.2 R2：动态变量提取、实体绑定与会话传递（`runner.go`、`execute.go`、`model_proof.go`）

1. **`AdapterCall` 与 `RunnerStep` 扩展**（全量 `omitempty` 以兼容原有严格 JSON 清单）：
   - 在 `AdapterCall` 新增：
     - `Headers map[string]string`（非凭据类可配置业务头，如 `Gateway-Version`、`X-Request-Id`，支持模板渲染，继续禁止包含敏感密钥字段名）；
     - `UseSession string`（引用本运行中某参与者的持久化会话，如 `"admin"`，自动注入提取的 Bearer Token 或挂载该参与者专属 `http.CookieJar`）；
     - `SessionHeader string` / `SessionPrefix string`（如 `Authorization` + `"Bearer "`，默认 `Authorization` / `"Bearer "`）；
     - `CookieJar bool`（为同一 `actor` 别名复用同一 `http.CookieJar`）；
     - `Extract []ExtractRule`（动作/Setup 成功后提取变量与实体绑定）。
   - `ExtractRule` 结构：
     ```go
     type ExtractRule struct {
         Name        string `json:"name"`                   // 变量名，如 payment_order_id
         Source      string `json:"source"`                 // response_body | response_header | cookie | oracle
         OracleID    string `json:"oracle_id,omitempty"`    // source=oracle 时必填
         Path        string `json:"path"`                   // JSON pointer 或 header/cookie 名
         EntityKind  string `json:"entity_kind,omitempty"`  // 非空时写入 run_entity_bindings，如 payment_order
         EntityAlias string `json:"entity_alias,omitempty"` // 默认同 Name
         OwnerActor  string `json:"owner_actor,omitempty"`  // 默认当前 step.Actor
         Required    bool   `json:"required,omitempty"`     // 提取失败是否立即阻断
         Secret      bool   `json:"secret,omitempty"`       // true 时仅存内存会话表并写入 digest，明文绝不入库/RAW
     }
     ```
2. **模板渲染规则（确定性可追溯）**：
   - 支持在 `Path`、`Body`、`Headers`、`Args` 中使用显式占位符：`{{var.<name>}}`、`{{actor.<alias>.principal}}`、`{{actor.<alias>.account}}`、`{{run.id}}`、`{{run.nonce}}`。
   - 未定义占位符立即 fail-closed 返回错误，绝不发送未渲染字符串或回退默认值。
   - **双哈希防篡改校验**（[model_proof.go](file:///Users/iluwen/Documents/Code/Skills/tools/arc-verify/model_proof.go#L110-L113)）：
     - `ActionObservation` 保留 `RequestSHA256`（实际发出的脱敏规范化请求摘要）并新增 `TemplateSHA256`（冻结清单中原始 `step.Call` 的摘要）与 `ResolvedInput json.RawMessage`（脱敏后的实际入参，用于入库展示）。
     - `modelObservationVerdict` 校验：`TemplateSHA256` 必须等于冻结 `step.Call` 摘要（或无模板时兼容 `RequestSHA256 == digest(step.Call)`），且结合该步运行绑定重算渲染后的请求摘要必须与 `RequestSHA256` 一致（涉及 `secret` 变量的仅校验脱敏占位摘要，不把明文 token 写入 `ResolvedInput` 或 `RAW`）。
3. **动态实体绑定持久化**：
   - 每一步 `Extract` 产出的非敏感变量与实体绑定立即记录到当前步 `StepFact.Extractions` 与 `run_entity_bindings` 表，后续步骤的 `Call` 和 `Oracles`（含 `OracleAdapter.Call.Path` / `Body` / `Args`）均可引用 `{{var.<name>}}`，实现"步骤 2 产生订单 `P` → 步骤 3/4/5 用同一 `P` 查询、投递、退款 → 独立 Oracle 按同一 `P` 回读核对归属"。

### 3.3 R3：有界异步等待契约（`runner.go`、`execute.go`、`model_proof.go`）

1. **`RunnerStep.AsyncWait *WaitContract`**：
   ```go
   type WaitContract struct {
       OracleID                  string              `json:"oracle_id"`
       UntilState                string              `json:"until_state,omitempty"`
       UntilConditions           ConditionAssignment `json:"until_conditions,omitempty"`
       UntilChecks               []PropertyCheck     `json:"until_checks,omitempty"`
       AllowedIntermediateStates []string            `json:"allowed_intermediate_states,omitempty"`
       MaxWaitMS                 int                 `json:"max_wait_ms"`     // 50 .. 120000
       PollIntervalMS            int                 `json:"poll_interval_ms"`// 25 .. 10000
       StableWindowMS            int                 `json:"stable_window_ms,omitempty"`
       RuleSourceRef             string              `json:"rule_source_ref"` // 必须指明规则/合同出处
   }
   ```
2. **校验与执行语义**：
   - `validateManifest` 校验 `OracleID` 必在 `step.Oracles` 内，`RuleSourceRef` 非空，所有声明状态在模型中存在，且 `MaxWaitMS <= manifest.StepTimeoutMS`（或步预算内显式覆盖，不得超过总超时）。
   - `execute.go` 动作执行后：若无 `AsyncWait`，保持原有单次 `readOracle`；若有 `AsyncWait`，在有界 `deadline` 内按 `PollIntervalMS` 轮询指定 Oracle：
     - 每次读取若出现传输错误（非网络瞬态或超时耗尽）→ `BLOCKED`；
     - 若读到既非目标态也不在 `AllowedIntermediateStates` 内的状态 → 立即提前停止并记 `FAIL`（保留非法中间态轨迹）；
     - 目标成立且满足 `StableWindowMS`（若配置）→ 结束等待并继续其余层 Oracle 读回；
     - 超时未达成 → 按最终实际读数判定 `FAIL`（产品未在约定窗口收敛）或 `BLOCKED`，完整保留 `WaitObservation`（起止时间、轮询次数、观察到的中间态序列、是否超时、最终状态、规则依据）。
